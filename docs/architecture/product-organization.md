# 작업 중심 앱 구조

2026-09-07 UI/UX 정리. 기존 프로젝트·작업·볼트·예약 데이터는 유지하며, 화면의 역할과 진입점을 다음처럼 정리한다.

## 용어

`작업`이라는 한 단어가 성격이 다른 네 개념을 가리키고 있었다. 저장 형식과 수명주기가 서로 다르므로 화면 이름도 나눈다.

| 개념 | 저장 | 이름 | 설명 |
| --- | --- | --- | --- |
| `WorkItem` | `<vault>/work/<id>/work.md` + 고정 workflow 의 산출물 | **작업** | 요청에서 시작해 설계·승인·실행·검증으로 이어지는 작업 단위. 하나의 워크플로로 진행하며 상태는 진행과 수락·종료 결정의 요약이다. |
| `TaskDef` | 호스트 작업 정의(프롬프트 + 선택적 `schedule`) | **자동화 작업** | 저장해 둔 에이전트 실행 내용. 예약 여부는 같은 정의의 실행 방식일 뿐이다. |
| `TodoItem` | 오늘 일지 문서의 체크박스 줄 | **할 일** | 일지에 적는 개인 체크리스트. 볼트 문서의 일부다. |
| `Job` · `HarnessRun` | 잡 큐, `<vault>/runs/<id>.md` | **실행** | 위 정의·항목을 실제로 돌린 인스턴스와 그 기록. |

작업은 요청에서 시작해 설계·승인·수행으로 끝나는 단위이고, 자동화 작업은 반복 업무를 에이전트에게 맡기는 수단이다. 둘은 사이드바에서 `작업`과 `자동화`로 갈라 두며 서로의 목록에 섞지 않는다.

`실행` 은 잡과 하네스 런 한 가지만 가리킨다. 예전에는 진입점 이름, `TaskDef`, 잡, `executionType`, 이슈 흐름의 노드, `plan` 산출물까지 여섯 개가 같은 낱말을 썼다. 지금은 진입점이 `에이전트`, `TaskDef` 가 `자동화 작업`, `executionType` 이 `처리 유형`, 이슈 노드가 `수행`, `plan` 산출물이 `계획` 이다.

| 진입점 | 역할 | 하위 화면 |
| --- | --- | --- |
| 작업대 | 현황을 모아 보는 위젯 대시보드 | 위젯 추가, 이동, 크기 조절 |
| 작업 | 하나의 의도와 완료 기준을 가진 작업을 관리 | 목록·공정 보드, 마일스톤, 공정 결정, 산출물 편집 |
| 자동화 | 저장해 둔 자동화 작업과 그 실행 시간 | 자동화 작업, 예약과 반복 |
| 캘린더 | 기한과 일정 | 작업 기한, 약속·마일스톤 |
| 프로젝트 | 프로젝트와 문서 관리 | 프로젝트 카드에서 자료 가져오기·문서 만들기 |
| 에이전트 | 에이전트와 실행 결과 | 터미널, 개발 실행, 협업 세션, 실행 기록, 검토 |
| 볼트 | 볼트의 문서 열람·유형별 보기·상태 점검 | 모든 문서, 할 일, 일지, 개념, 점검 |
| 확장 기능 | 설치된 기능을 사용 | 읽을거리, 설치된 GitHub |
| 확장 관리 | 기능·스킬·워크플로 설치와 관리 | 설치됨, 마켓플레이스, 스킬, 워크플로 |
| 설정 | 앱 환경과 볼트 구조 | 일반·실행 설정, 볼트 문서 구조 |

작업은 하나의 진입점에서 목록과 공정 보드를 전환한다. 두 보기는 같은 필터·작업 상세·결정 동작을 공유한다. 프로젝트·설정에는 전역 하위 탭을 두지 않는다. 프로젝트를 고른 상태에서 문서 만들기를 열고, 설정에서 볼트 문서 구조를 연다. 확장 관리는 서로 다른 대상을 한 화면에 섞지 않고 `설치됨 / 마켓플레이스 / 스킬 / 워크플로` 탭으로 나눈다. 자동화의 정의·예약 전환과 실행 도구의 전환은 같은 업무 범위이므로 탭으로 유지한다. 화면 헤더에는 기능명과 조작만 두며 브랜드 문구·감성 제목·반복적인 소개 문단을 표시하지 않는다.

전체 검색과 알림센터는 앱 상단에 항상 있다. 전체 검색은 볼트 문서, 작업, 프로젝트, 자동화 작업, 실행 기록을 함께 찾는다. 알림은 실행 종료·실패, 놓친 예약, 승인 요청, 에이전트 입력 대기·검토, 확장 로드 오류를 모으며 읽음 상태를 저장한다.

## 자동화: 자동화 작업과 예약

기존 `TaskDef`의 실행 내용과 선택적인 `schedule`을 사용한다. 수동·한 번·매일·평일은 서로 다른 종류가 아니라 같은 정의의 실행 방식이다. 활성 팩이 선언한 모든 액션과 호스트의 `인박스 승격 검토`도 같은 “자동화 작업” 목록에 표시한다. 파라미터가 있는 팩 액션은 목록에서 입력값을 받은 뒤 실행한다. 예약 화면에서는 이 중 예약된 정의와 사용자가 예약할 수 있는 정의를 다루며 제목과 프롬프트를 복제하지 않는다. 작업(`WorkItem`)과 자동화 작업(`TaskDef`)은 기존 저장 형식을 그대로 유지한다 — 바뀐 것은 화면의 이름과 배치뿐이다.

앱 시작 시 예약 실행기를 연결한다. 예약 없는 정의도 저장된 내용에서 즉시 실행할 수 있다. 기본 제공 행은 실제 활성 확장의 예약 엔트리에서 만들며, 토글과 시간 수정은 해당 엔트리의 키에 적용한다. 실행 시간의 기준은 데스크톱의 로컬 시간이다.

## 대시보드 복구

`6184877`의 `DashboardBoard`, `layout-store`, `registry`를 현재 `app/`에 복구했다. `react-grid-layout`으로 이동·리사이즈하며 넓은·중간·좁은 화면의 배치를 각각 저장한다. 레이아웃 v1/v2/v3과 예전 `sawhorse.overview-slots` 표시 설정을 v4로 읽는다. 이관은 첫 로드에서 바로 저장해 옛 판이 남지 않는다. 사용자가 모든 위젯을 숨긴 상태도 유지한다.

개발·캘린더·이슈·실행·자동화·볼트·읽을거리에서 제공하는 위젯을 카탈로그에 등록한다. 볼트로 옮긴 `할 일`은 작업대 위젯으로도 기본 표시한다. 외부 확장이 임의의 JavaScript 위젯을 실행하는 API는 추가하지 않았다. 카탈로그는 카테고리로 묶고 이름·설명 검색을 제공한다.

### 지표 카드

숫자 카드는 묶음 위젯 하나가 아니라 카드 한 장이 위젯 하나다(`metric:<키>`). 어떤 숫자를 볼지는 사람마다 다르므로 — 제안이 몇 건 쌓였는지, 승인이 몇 건 밀렸는지 — 카드를 고정하지 않고 낱개로 켜고 끄고 자리와 크기까지 따로 정하게 한다. 정의는 `app/src/features/dashboard/metrics.ts` 한 곳에 모아 두고, 화면은 정의를 보고 그리므로 지표를 늘려도 분기가 늘지 않는다.

| 묶음 | 지표 |
| --- | --- |
| 상태 | 제안, 승인 대기, 실행 대기, 진행 중, 완료, 보류 |
| 기한 | 기한 초과, 오늘 마감, 7일 내 마감 |
| 처리 | 담당 지정, 승인 필요, 보류, 반려·취소 |
| 활동 | 오늘 완료, 최근 7일 완료, 실행 중, 실행 실패 |

상태 지표의 분류는 이슈 위젯의 상태 분포(`ISSUE_GROUPS`)와 같은 어휘를 쓴다. 기한·담당 지표는 완료·반려·취소가 아닌 열린 항목만 센다. 기본 대시보드는 예전 묶음이 보여주던 진행 중·실행 대기·기한 초과·완료 넉 장으로 시작하고, v3 이하의 `metrics` 한 칸은 같은 자리에서 이 넉 장으로 펼쳐진다.

## 문서 명칭

`노트`를 문서와 별도의 제품 개념으로 노출하지 않는다. 마크다운 파일은 모두 `문서`이며, `일지`와 `개념`은 볼트 문서의 유형별 보기다. 사이드바는 상위 `볼트` 카테고리 아래에 `모든 문서`·`할 일`·`일지`·`개념`·`점검`을 묶는다. `할 일`은 오늘 일지 문서의 체크리스트를 편집하는 화면이므로 볼트에 둔다. `모든 문서`는 전체 파일 트리, `일지`와 `개념`은 해당 문서 목록, `점검`은 볼트 검사와 미승격 항목을 담당한다. 기존 `기록/`과 `노트/` 작업공간은 읽기 호환성을 유지하고, 새 작업공간은 `일지/`와 `문서/`를 사용한다.

## 확장과 연결

읽을거리(`core-feeds`)는 켜고 끌 수 있는 코어 확장이다. GitHub는 `plugin/connector-extensions/github/extension.json`에 별도 manifest로 둔다. 확장 관리에서 설치하면 사용자 확장 디렉터리에 manifest를 배치하고 사이드바 `확장 기능` 아래에 GitHub 페이지를 표시한다. 기존 연결 데이터는 비활성화해도 보존한다. 비활성화한 연결의 동기화 명령은 백엔드에서도 거절한다.

RSS 소스 화면에는 RSS 연결만, 이슈 연동 화면에는 GitHub 연결·가져오기·원격 변경 검토만 표시한다. 연결 권한과 원격 쓰기 승인 경로는 기존 브로커를 사용한다. GitHub 전용 관리 화면은 브라우저 OAuth 승인을 시작하고 발급된 자격 증명만 OS 키체인에 저장한다. 설치 여부와 사용 여부는 별개이며, 사용을 중지해도 설치된 확장과 관리 진입점은 남는다.

관리 화면은 계정이 접근할 수 있는 저장소를 50개씩 불러온다. 검색은 현재 불러온 목록에 적용되며 더 보기로 이어서 읽는다. 저장소의 immutable ID와 계정은 이슈 연결 시 자동 입력된다. 프로젝트로 가져오기는 선택한 로컬 폴더에 Git clone을 수행하고 프로젝트를 등록한다. 계정 연결은 GitHub OAuth Device Flow를 사용하며 Client Secret이나 PAT를 UI에서 받지 않는다. 발급된 OAuth 토큰과 선택적인 refresh token은 OS 키체인에 하나의 자격 증명으로 저장한다. 토큰은 Git의 프로세스 환경에서만 전달하고 저장소 설정이나 URL에 넣지 않는다. 같은 이름의 기존 폴더는 대체하지 않으며, 3분 내 완료되지 않으면 프로세스를 종료하고 이 작업이 만든 임시 폴더를 정리한다. 가져온 프로젝트에서 코드베이스를 입력으로 문서 초안을 만들 수 있다.

GitHub 저장소 목록 계약: [GitHub REST 문서](https://docs.github.com/en/rest/repos/repos#list-repositories-for-the-authenticated-user).

## 하나의 작업 생명주기

이슈와 개발 메뉴를 `작업` 하나로 통합한다. 목록은 요청 유형·우선순위·담당자·기한·마일스톤을 정리하고 공정 보드는 작업에 고정된 워크플로 버전별 현재 노드를 보여준다. GitHub 이슈는 외부 연결 정보이며 별도 내부 생명주기를 만들지 않는다. 과거 `board`·`issues` 진입점은 작업으로 연결한다.

작업 생성은 접수다. 요청 수락은 예정, 착수와 공정 전환은 진행으로 이어진다. 중간 설계 승인은 작업 전체의 결과 검토가 아니다. 마지막 공정의 입력·출력 근거와 의존 작업 완료를 확인한 뒤 결과 검토를 요청하고, 최종 인수 결정으로 완료한다. `End` 노드가 있는 워크플로는 해당 노드 진입 결정으로 완료한다. 반려는 접수된 요청을 받지 않는 결정이고, 취소는 받아들인 일을 중단하는 결정이다. 보류·재개는 공정 위치를 보존한다. 닫힌 작업은 실행·전환할 수 없으며 후속 작업을 만들 수 있다.

`workflow_command`가 공정 이벤트와 `work:accept/start/submit/complete/revise/pause/resume/reject/cancel` 결정을 처리한다. `status`는 이 결정들의 요약이고 `state`와 `closed`는 status에서 파생한다. 메타데이터 편집·대시보드·목록은 status나 approve를 직접 변경하지 않는다. 기존 approve/approved 필드는 이전 클라이언트를 위한 호환 정보로 보존하지만 별도 승인 체크는 제공하지 않는다. 에이전트 런의 종료·검토 대기 신호는 작업 전체의 상태를 바꾸지 않는다.

저장소는 `work/<id>/`를 유지하며 기존 워크플로 digest와 결정 이력은 바꾸지 않는다. 예전 중간 공정에 남은 예정·검토 상태는 읽을 때 진행으로 해석한다. 기존 완료·반려·취소 기록은 보존한다. `issue-main`과 `sdd-main` 등 기존 워크플로는 그대로 사용할 수 있다. 마지막 노드가 End가 아닌 고정 버전도 결과 인수 동작으로 닫을 수 있다.

레거시 이슈 노트는 작업 화면 아래에서 이관하며 원본을 삭제하지 않고 `migrated_to`만 기록한다. 이관은 원본의 상태와 승인 이력을 보존한다.

## 마일스톤

마일스톤의 이름과 기한은 `calendar/*.md` 일정에 저장하며, 구성원은 작업의 `milestone` 필드가 정본이다. 작업 화면과 캘린더가 같은 일정 편집기를 사용한다. 마일스톤 관리는 작업 화면의 사이드바 한 곳에만 노출하고, 팩이 별도 마일스톤 문서 화면을 사이드바에 추가하지 않는다. 항목을 다른 마일스톤에 넣으면 해당 필드를 바꾸므로 중복 소속되지 않는다. 완료 진행률은 구성원의 `state: closed` 비율이다. 기존 볼트의 마일스톤 참조도 별도 그룹으로 유지한다.

마일스톤에 항목이 남아 있는 동안 일정 삭제나 일반 일정으로의 변경을 거절한다. 작업과 아직 이관하지 않은 레거시 노트를 모두 센다. 볼트 진단도 캘린더 마일스톤을 유효한 참조로 인정한다. 여러 항목 변경은 각 파일을 원자적으로 저장하며, 중간 실패 시 오류를 표시하고 현재 상태를 다시 읽는다. 볼트 전체를 대상으로 한 다중 파일 트랜잭션은 아니다.

## 프로젝트 폴더 이름

사람이 읽는 프로젝트 문서는 `프로젝트/<이름>/` 아래에 둔다. 사내 SI 전용이던 시절의 `사업/` 은 계속 읽지만 새로 만들지 않는다. 두 폴더가 함께 있으면 정본인 `프로젝트/` 만 읽어 같은 항목이 두 번 잡히지 않게 한다. 실제 볼트의 폴더 이동은 앱이 자동으로 하지 않는다.

## 편집 경험

워크플로는 드래그 가능한 단계 캔버스와 시작 단계·조건·다음 단계를 선택하는 연결 폼으로 편집한다. 단계의 위치는 초안 ID별로 로컬 저장한다. 문서 구조 설정은 입력 형식을 텍스트·숫자·정수·예/아니요·선택 목록으로 고르며 기존 복잡한 정의는 고급 JSON에서 편집한다.

실제 PC의 파일·폴더 경로 입력은 공통 `PathInput`과 Tauri Dialog를 사용한다. 볼트, 프로젝트, 실행 파일, 확장 패키지, 가져올 자료, GitHub 문서·저장소 경로에 적용한다. 볼트 내부의 상대 경로 패턴은 운영체제의 실제 경로가 아니므로 텍스트로 편집한다.

## 마켓플레이스 형식

사용자가 지정한 HTTPS JSON 카탈로그를 읽는다. 기존 다른 서비스의 임의 마켓플레이스 형식을 자동 변환하는 기능은 아니다. 카탈로그 선택은 설치 소스만 채우며 패키지 검증·설치와 프로젝트 권한 적용은 기존 경로를 사용한다. 스킬은 확장 패키지의 `contributions.skills`를 통해 배포한다.

```json
{
  "name": "팀 확장",
  "packages": [
    {
      "id": "team-skills",
      "name": "팀 스킬",
      "category": "skill",
      "description": "팀에서 사용하는 에이전트 스킬",
      "source": {
        "kind": "https",
        "location": "https://example.com/packages/team-skills.json"
      }
    }
  ]
}
```

Git 소스는 HTTPS 저장소 주소와 정확한 40자리 `commit`을 함께 지정한다. 카탈로그는 2MB로 제한하고 중복 ID·로컬 소스·고정되지 않은 Git 소스를 거절한다.

## 검증 범위

Playwright는 명시적인 `?preview=1` 데이터로 위젯 이동·리사이즈·설정 유지, 자동화 작업의 반복 예약, 볼트 카테고리에 묶인 문서 화면과 `할 일`, 확장 설치에 따른 화면 기여, RSS/GitHub 분리, 시각 편집과 작업·문서 흐름, 그리고 작업 화면과 공정 보드이 같은 항목을 보여 주는지를 검증한다. Rust 테스트는 실제 manifest, 카탈로그 검증, 예약과 실행 경로, 저장소 이름 검증, 마일스톤 참조 무결성과 YAML 필드 보존, `status` 에서 파생하는 열림·닫힘, 레거시 이슈 노트 이관의 멱등성과 원본 보존, 예전 `사업/` 폴더 폴백을 검증한다. 협업 인박스 테스트는 사용자 경로 대신 테스트별 임시 경로를 사용한다.

실계정 GitHub 인증·저장소 복제·동기화와 운영체제 파일 선택창의 클릭·선택은 데스크톱에서 별도 확인이 필요하다. 브라우저 체험에서는 실제 계정·파일·에이전트를 연결하지 않는다.

## 프로젝트별 작업대와 공정 범위

작업대의 `전체 프로젝트` 선택은 작업·캘린더·에이전트 실행·작업 문서 검색으로 이어지는 공통 프로젝트 범위다. 새 작업과 일정도 선택한 프로젝트로 시작한다. 프로젝트 목록에서 `작업대 열기`로 바로 진입할 수 있다. 프로젝트 선택과 위젯 배치는 브라우저/데스크톱의 로컬 UI 설정으로 저장한다. 전체 작업대의 기존 배치와 사용자가 모든 위젯을 숨긴 상태는 유지한다.

전체 작업대는 프로젝트별 공통 상태와 기한을 요약한다. 프로젝트 작업대의 기본 구성은 진행·결과 검토·보류·기한, 공정 현황, 다음 작업, 실행, 작업 문서, 일정이다. 개인 일지의 할 일·RSS·프로젝트 소속이 없는 예약 위젯은 전체 작업대에 둔다. 상단 `전체 검색`은 선택한 프로젝트와 관계없이 전체 작업공간을 검색하며, 프로젝트 작업대에서 들어간 문서 검색은 그 프로젝트의 작업에 연결된 산출물을 검색한다.

워크플로우가 달라지면 공정 단계·필요한 문서·전환 조건·반복 구조가 달라진다. 따라서 전체 프로젝트를 하나의 공정 칸반으로 합치지 않는다. 공정 보드와 단계별 현황 모두 실제 작업의 활성 워크플로우 ID와 버전별로 나누며, 하위 워크플로우는 현재 활성 노드를 기준으로 센다. 같은 이름의 단계도 단계 필터에서 워크플로우와 버전으로 구별한다. 완료·반려·취소한 항목은 진행 중 단계 집계에 넣지 않는다.

프로젝트의 기본 워크플로우를 변경해도 기존 작업의 고정된 흐름은 유지한다. 프로젝트 작업대에는 현재 기본 흐름과 기존 작업의 흐름이 함께 나타날 수 있다. 작업이 없는 프로젝트도 설정된 공정의 빈 현황을 표시한다. 공통 업무 상태는 비교용 요약이며, 워크플로우별 실제 공정을 대체하는 새로운 생명주기가 아니다.

### 사이드바의 프로젝트 범위

사이드바의 `프로젝트별 화면` 영역은 공통 프로젝트 선택기 아래 작업대·작업·캘린더·개발 실행·실행 기록·작업 문서 검색을 묶는다. 화면 안의 프로젝트 선택기와 같은 선택을 공유한다. 프로젝트 선택은 데이터 범위를 바꾸며 공통 화면에서 다른 프로젝트를 선택해도 현재 화면을 이동시키지 않는다.

자동화 정의·프로젝트 관리·워크플로우 편집기·전체 에이전트 터미널과 협업·검토는 `전체 작업공간`에 둔다. 기존 에이전트 탭에서 프로젝트에 종속된 개발 실행·실행 기록을 꺼내 프로젝트 영역으로 옮겨 한 메뉴 안에서 범위가 섞이지 않게 한다. 볼트와 확장 기능에는 `공통`을 표시한다. 볼트는 프로젝트 선택에 따라 다른 저장소로 바뀌지 않는다.

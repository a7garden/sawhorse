# 워크플로우 라이브러리

워크플로우 화면의 기본 진입점은 갤러리다. 제작 도구를 열기 전에 용도와 운영 방식부터 비교한다. 번들은 팀이 복제하거나 개정할 수 있는 출발점이며, 사용자·확장 워크플로우도 같은 카탈로그와 편집기를 사용한다.

## 기본 번들

이름은 `방식 · 설명` 형식을 따른다. 진행 방식은 이름으로, 실행 단계와 운영 방식은 설명과 비교 정보로 안내한다.

| 이름 | ID | 최신 버전 | 용도 |
|---|---|---|---|
| SDD · 명세 기반 개발 | `sdd-main` | 1.1.1 | 명세·구현·검증·배포 기록 |
| Intent · 의도 기반 개발 | `intent-flow` | 2.0.1 | 아이디어 구체화·인터뷰·승인·구현 |
| TDD · 테스트 기반 개발 | `tdd-cycle` | 1.0.1 | Red·Green·리팩터링·회귀 검증 |
| SDD + TDD · 명세·테스트 기반 개발 | `sdd-with-tdd` | 1.1.1 | 명세 기반 흐름에 TDD 하위 흐름 결합 |
| Issue · 요청 해결 | `issue-main` | 1.1.1 | 요청·설계·승인·수행 |
| Goal · 목표 달성 | `goal-main` | 1.0.1 | 명확한 목표를 자율 수행 |

기존 여섯 종류의 이름 변경은 새 patch 버전으로 제공한다. 이전 정의와 digest, 하위 흐름의 정확한 버전 참조는 유지한다. 기존 프로젝트는 고정한 이름과 버전을 계속 표시하며, 최신 이름을 사용하려면 프로젝트 설정이나 갤러리에서 새 버전을 적용한다. Intent 2.0.0/2.0.1과 Goal 1.0.0/1.0.1은 각각 같은 전용 생성·실행 경로를 지원한다.

작업의 목적은 워크플로우와 독립된 `issueType`으로 저장한다: 기능 추가(`기능`), 버그 수정(`버그`), 리팩토링(`리팩토링`), 일반 작업(`작업`), 질문(`질문`). 기존 필드를 확장하므로 중복 분류를 만들지 않는다. SDD로 버그를 수정하거나 TDD로 리팩토링할 수 있다. 유형별 작성 틀·입력 안내·에이전트 검증 기준은 제공하지만 노드, 승인, 산출물 계약을 바꾸지 않는다. Intent와 Goal 생성도 같은 유형을 저장하며 Goal의 하위 작업은 부모 유형을 이어받는다.

초기 프로토타입 `bugfix-main`과 `refactor-main`은 기존 작업 재개를 위한 불변 정의로만 유지한다. 갤러리와 프로젝트 선택지에서는 제외하고 호스트의 프로젝트 저장·적용·신규 작업 생성에서도 선택을 거부한다. 이미 이 흐름을 기본값으로 저장한 프로젝트를 읽을 때는 기반 방식인 SDD 1.1.1로 정규화하고 추가 사용 목록의 두 프로토타입을 제거한다. 다음 프로젝트 저장 시 정규화한 설정이 저장된다. 기존 작업의 ID·버전·digest·문서·실행 기록은 변경하지 않고 ‘기존 작업만’ 보기에서 연다.

브라우저 카탈로그 `samples/workflows.json`은 Rust 번들 카탈로그를 내보낸 것이며, 동등성 테스트로 누락과 내용 차이를 확인한다. 갱신 시 사용자 워크플로우가 없는 임시 디렉터리를 `--vault`로 지정하고 CLI의 `--json workflow list` 응답에서 `data`를 저장한다.

## 선택과 버전

- 카탈로그의 같은 ID는 한 종류로 묶고 SemVer상 최신 버전 한 장을 표시한다. 사전 출시 버전도 SemVer 순서를 따르며 build metadata는 우선순위에 영향을 주지 않는다.
- 이전 버전은 상세와 라이브러리의 접힌 이력에서 열 수 있다. 버전별 기본 프로젝트와 작업 수를 표시한다.
- 프로젝트 생성 창은 종류별 최신 버전을 제시한다. 기존 프로젝트 편집 창은 현재 고정된 버전도 유지한다.
- 갤러리의 프로젝트 적용은 기존 `workflow_activate` 명령을 사용한다. 프로젝트의 새 작업 기본값만 바꾸며 기존 작업의 정확한 버전과 digest는 유지한다.
- 화면에서 숨기는 것과 저장본을 삭제하는 것은 별개다. 작업·하위 흐름이 참조할 수 있는 발행본은 삭제하거나 다시 쓰지 않는다. 프로토타입 프로젝트 기본값의 호환성 정규화 외에는 고정한 흐름을 자동 전환하지 않는다.

## 비교 정보

용도 안내는 UI에 두고 불변 정의와 digest를 변경하지 않는다. 사용자 정의 흐름은 정의의 description을 안내로 사용한다. 단계 구성, 명시된 human 노드 수, 산출물, 선언된 반복 한도, 정확한 하위 흐름 참조는 실제 정의에서 계산한다. 단계 칩은 노드 목록이며 분기 그래프의 실행 순서를 의미하지 않는다.

최대 세 흐름을 나란히 비교한다. human 노드 수는 자동화 수준을 완전히 표현하지 않으므로 승인 이벤트와 하위 흐름의 사람 참여는 전체 흐름에서 확인하도록 안내한다. 골 모드처럼 에이전트 내부에서 반복하는 동작은 선언형 loops와 구분한다.

## 만들기와 공유

1. 새 워크플로우를 만들거나 기존 흐름을 독립 ID와 1.0.0 버전의 초안으로 복제한다.
2. 공유받은 JSON은 기존 import API를 통해 초안으로 저장한다. 가져오기가 바로 발행이나 프로젝트 적용을 의미하지 않는다.
3. 기존 편집기에서 단계·산출물·하위 흐름·요구사항을 검토하고 검증·시뮬레이션한 뒤 발행한다.
4. 내보내기는 유효한 정의 JSON을 클립보드에 복사한다. 수신자는 가져오기에서 붙여 넣는다. 하위 흐름을 사용하는 정의는 참조하는 정확한 버전들도 별도로 제공해야 한다.
5. 여러 워크플로우와 도구의 배포는 기존 확장 package v2의 workflows 기여를 사용한다. 갤러리에서 확장 관리로 이동할 수 있다.

중앙 커뮤니티 마켓, 원격 검색, 작성자 인증은 이 로컬 공유 경로에 포함되지 않는다. 출처를 알 수 없는 정의에 번들·공식·신뢰됨 배지를 추정해 붙이지 않는다.

## 프로젝트 작업대와 생성 범위

프로젝트는 저장소·에이전트·공통 설정의 범위이며, 워크플로우 정의를 소유하지 않는다. 여러 프로젝트가 같은 라이브러리 정의를 재사용한다.

- `workflowId`, `workflowVersion`, `workflowDigest`는 새 작업의 **기본값**이다. 추가 사용 흐름은 `additionalWorkflows: [{ id, version }]`에 정확한 버전으로 저장한다. 기본 흐름은 항상 사용 가능하며, 이 필드가 없는 기존 프로젝트는 기본 흐름 하나만 사용한다.
- 프로젝트 설정에서 추가 흐름을 선택·해제한다. 기본값을 바꾸거나 갤러리·CLI로 새 기본값을 적용하면 이전 기본 흐름도 사용 목록에 남긴다. 흐름을 해제해도 기존 작업의 정의·문서·실행은 유지한다.
- 작업대의 보기 선택에는 사용 가능한 흐름과 기존 작업이 참조하는 흐름을 함께 표시한다. 후자만 남은 흐름은 ‘기존 작업만’으로 표시하고 새 작업 생성은 막는다. 다른 버전은 별도의 보드로 구분한다.
- 여러 흐름이 있으면 처음에는 **전체 작업** 목록을 보여준다. 인박스·진행·완료·보관 작업을 함께 나열하고, 각 작업의 흐름·정확한 버전·실제 단계·상태를 표시한다. 전체 목록의 상태 필터는 공통 상태를 사용한다.
- 특정 흐름을 선택하면 해당 버전의 단계 보드 또는 목록을 표시하고, 새 작업에는 그 흐름을 제안한다. 전체 보기에서는 프로젝트 기본 흐름을 제안한다. 한 흐름만 있으면 기존 보드를 유지하고 보기 선택기를 숨긴다. 보기 선택은 프로젝트별로 기억한다.
- 여러 흐름을 사용하는 프로젝트의 생성 창에서는 프로젝트와 흐름을 고른 다음 해당 입력 양식으로 진행한다. 입력을 시작한 뒤에는 선택을 고정해 화면 갱신으로 초안이 사라지지 않게 한다. Intent·Goal도 추가 흐름으로 사용할 수 있다.
- 일반 작업 저장·의도 캡처·목표 생성 모두 호스트에서 선택한 정확한 버전이 현재 프로젝트의 사용 목록에 있는지 검사한다. 작성 중 그 버전이 제거되면 저장을 거부하고 초안을 유지한다. 기본값만 바뀌고 선택한 흐름이 남아 있으면 계속 저장할 수 있다.
- 이미 생성한 작업은 정확한 버전과 digest에 고정한다. 프로젝트 기본값·사용 목록·카탈로그 최신 버전은 기존 작업을 자동 전환하지 않는다. 내부 가져오기와 하위 워크플로우 저장은 별도 정의를 유지한다.

작업 유형은 모든 흐름의 목록과 카드에 표시하고 독립적으로 필터링한다. 작업 유형을 바꾸어도 워크플로우와 보드는 바뀌지 않는다.

Intent 전용 인박스·보관 영역은 Intent 단계 보드에서만 사용한다. SDD·TDD 같은 일반 흐름의 입력 노드는 해당 보드에 그대로 표시한다.

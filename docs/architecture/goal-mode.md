# 골 모드와 작업 점유

새 의도 작성 창에서 **골 모드**를 선택하고 프로젝트, 목표·완료 기준, 최대 병렬 작업 수를 입력한다. **자율 실행 시작**은 설계와 구현을 포함한 목표 수행을 승인한다. 이후에는 단계 승인 없이 작업 생성, 설계, 구현, 독립 검증을 반복한다. **목표 저장**은 일시 정지 상태로 저장한다.

게임 제작이나 남은 사용량을 활용한 장기 작업에 사용할 수 있다. 고정 반복 횟수나 재시도 횟수 제한은 없으며, 시간이나 토큰이 부족하다는 이유로 완료 처리하지 않는다. 목표 달성 여부는 별도 verifier 실행이 실제 확인 결과를 제출한 뒤 판정한다. 구현자의 완료 보고는 검증 실행을 요청할 뿐이다.

## 여러 작업 일괄 실행

작업 흐름의 보드 카드나 목록에서 체크박스로 여러 항목을 선택한 뒤 **골 모드로 일괄 실행**을 누른다. 보드·목록 전환 시 선택을 유지하고, 검색·필터로 숨겨진 항목은 선택에서 제외한다. 한 번에 최대 100개를 접수한다.

일반 작업은 같은 작업 ID를 유지하면서 골 모드로 전환한다. 기존 문서, 의존 작업, 프로젝트, 분류는 유지하고 원래 작업 기록은 `work/<id>/goal-source.md`에 보존한다. 목표에는 기존 산출물 경로를 포함해 남은 의도와 수용 기준을 이어서 수행한다. 중지된 골 목표는 재개하고, 이미 큐에 있거나 토큰 복구를 기다리는 목표는 큐와 대기 시각을 그대로 유지한다.

항목별로 **실행 접수**, **이미 대기 중**, **건너뜀** 결과를 표시한다. 실행 중·종료된 작업, 부모가 관리하는 골 하위 작업, 목업 검토 항목은 건너뛴다. 별도 작업 트리에서 구현·통합·결과 확인이 진행된 SDD v2 항목도 기존 결과를 먼저 처리해야 한다. 일부 항목이 실패해도 다른 선택 항목은 접수하고, 실패 항목의 선택과 이유는 화면에 남긴다.

접수는 실행 완료를 뜻하지 않는다. 기존 점유, 의존성, 수정 범위와 전체 병렬 한도에 따라 큐가 실행하며, 완료된 다른 워크플로우의 작업도 선행 의존성으로 인정한다. 브라우저 체험은 큐 상태만 모의 저장하고 실제 에이전트를 실행하지 않는다.

## 실행과 복구

- `goal-main@1.0.0`은 사람의 승인을 받는 노드가 없는 기본 제공 워크플로우다. 프로젝트 기본 워크플로우를 바꾸지 않고 선택할 수 있다.
- 프로젝트 기본 에이전트가 Codex 또는 Claude인 경우 백그라운드 실행한다. 골 실행에만 비대화형 권한 정책을 적용한다. Codex는 `workspace-write`와 `approval_policy="never"`, Claude는 `bypassPermissions`를 사용한다.
- 앱의 하네스 틱이 목표 큐를 진행한다. 앱이 꺼져 있거나 컴퓨터가 잠들어 있으면 실행하지 않으며, 다시 실행되면 저장된 큐와 재시도 시각을 읽는다. 매시간 깨우는 OS 서비스나 유료 크레딧 구매는 하지 않는다.
- 사용량 한도·요청 속도 제한 오류는 **토큰 복구 대기**로 바꾸고 오류 발생 시각에서 3,600초 뒤에 실제 작업을 재시도한다. 실패하면 다시 3,600초 뒤로 미룬다. 성공하면 이어서 작업한다. 별도 사용량 조회 API는 필요하지 않다.
- 에이전트 종류별로 대기 시각을 공유해 같은 계정의 작업이 복구 전에 요청을 반복하지 않게 한다. 수동 재개도 이 대기 시각을 건너뛰지 않는다. 일반 오류는 근거를 다음 실행에 전달하고 20초 뒤 다시 시도한다.
- 일시 정지·취소는 해당 목표의 하위 실행에도 취소 요청을 남긴다. 프로세스가 정리된 다음 재개할 수 있다. 취소한 목표와 완료한 목표는 자동 재시작하지 않는다.

## 영속 상태와 완료 프로토콜

각 목표와 하위 작업은 일반 `work/<id>/work.md` 항목이다. 같은 디렉터리의 `goal.json`이 목표, 부모, 작업 목록, 실행 ID, 반복 번호, 변경 범위, 재시도 시각, 진행 근거를 저장한다. `work.md`의 상태는 이 정본에서 복구 가능한 화면용 값이다. `evidence.md`에는 에이전트가 실행 중 체크포인트를 남긴다.

에이전트는 `runs/<runId>.goal-result.json`에 `runId`, `action`, `evidence`, `checks`, `tasks`를 기록한다. action은 `tasks`, `continue`, `complete` 중 하나다. 성공적으로 종료한 실행의 파일만 읽으며 다른 실행 ID, 빈 근거, 실패한 검증, 중복 작업 키, 순환·누락 의존성, 잘못된 파일 범위를 거부한다. 마지막 터미널 문구나 프로세스 종료 코드만으로 목표를 완료하지 않는다.

하위 작업 정의를 먼저 저장하고 실제 작업 파일을 생성한다. 실행 접수는 목표 ID와 반복 번호를 키로 삼아 재시작 시 같은 실행을 복원한다. 각 구현 작업과 전체 목표에 독립 검증 실행이 있으며, 검증이 남은 문제를 찾으면 다시 구현하거나 수정 작업을 만든다.

## 공통 작업 점유와 병렬 실행

모든 워크플로우의 하네스 실행은 역할에 관계없이 **작업당 하나의 실행 트리**만 소유한다. `starting`, `running`, `blocked`, `unknown` 실행이 있으면 다른 루트 실행은 거부된다. 기존 일반 워크플로우의 하위 에이전트는 활성 부모의 점유 안에서 보조 작업을 수행하며, 기존 트리의 하위 실행이 남아 있어도 새 루트는 시작하지 못한다.

접수 시 프로세스 내부 잠금과 `.sawhorse/locks/harness-launch.lock`의 OS 잠금으로 검사와 실행 기록 저장을 직렬화한다. 백그라운드 실행의 수명 잠금은 다른 Sawhorse 프로세스가 살아 있는 실행을 고아 실행으로 오판하지 않게 한다. 후속 실행도 같은 작업 점유를 확인한다.

골 모드는 병렬 작업마다 별도 작업 ID를 만든다. 의존 작업이 완료되고 변경 경로가 겹치지 않을 때만 실행한다. `src/game`과 `assets`는 동시에 실행할 수 있지만 `src`와 `src/game`은 순차 실행한다. 범위가 불확실한 `.`은 저장소 전체를 뜻한다. 일반 워크플로우와 골 작업이 같은 저장소를 사용할 때는 일반 워크플로우의 범위를 저장소 전체로 취급한다. 경로 범위는 에이전트 지시와 예약 충돌 검사에 사용하며 파일별 OS 샌드박스는 아니다.

최대 병렬 수는 목표별 1~16개이며 전체 하네스 실행 한도도 함께 적용한다. 목표 화면은 하위 작업, 점유 에이전트·실행 ID, 진행 근거와 다음 재시도 시각을 표시한다.

## 검증

Rust 테스트는 자동 분해 → 병렬 작업 → 의존 작업 → 독립 검증 → 전체 완료, 사용량 대기 지속, 취소·재개, 프로세스 간 점유 충돌, 소유 프로세스 복구를 모의 실행으로 검증한다. Playwright 테스트는 골 모드 작성·저장·상태 표시·취소와 승인 UI가 없는 것을 확인한다. 실계정 토큰을 소진시키는 테스트는 수행하지 않는다.

# SDD 작업 생명주기 v2

새 의도와 새 프로젝트의 기본 흐름은 `intent-flow@2.0.0`이다. 이미 시작한 v1 작업은 발행된 버전을 유지한다. 산업별 문서·업무 규칙은 선택 확장과 워크플로우 팩에 두며 코어에서 SI를 전제로 하지 않는다.

## 작업 화면

작업 화면의 기본 진입점은 하나의 생명주기 칸반이다. 구체화 → 설계 → 승인 대기 → 구현 대기 → 구현 → 완료·미확인 → 완료의 일곱 칸을 빈 프로젝트에도 표시한다. 의도는 별도 인박스에서 관리하며 작업 수와 작업 마일스톤 집계에 포함하지 않는다. 구체화 전에 취소한 의도도 작업 수에 포함하지 않는다.

상단에서는 인박스, 검토할 설계, 확인할 결과로 바로 이동한다. 하단의 작업 흐름·의도 인박스·보관함·목업 탭은 각 기록을 나누어 보여준다. 취소·반려·폐기는 보관함에, 정상 완료는 칸반의 완료 칸에 남는다. 칸반과 목록은 같은 작업과 필터를 사용한다.

기존 SDD·intent-flow 작업도 상태에 맞춰 같은 칸반에 배치한다. 이 표시는 저장된 워크플로우 버전·승인·실행 단계를 수정하지 않는다. 검증·배포 진행은 구현 영역에 원래 단계와 함께 표시하고, 최종 노드의 결과 검토는 완료·미확인으로 표시한다. 매핑할 수 없는 확장 단계는 이름을 추측하지 않고 기타 워크플로 칸에 원래 단계와 함께 표시한다. 기존 작업의 상세 결정은 원래 계약을 유지한다.

화면 재구성 검증: 빌드와 관련 브라우저/표시 규칙 검사 42개 통과. 기본 진입, 빈 프로젝트, 인박스에서 구체화로 이동, 작업 수에서 의도 제외, 검토 바로가기, 보관함, 기존 기록 불변, 목업, 좁은 화면, 영문·양쪽 테마, 목표 모드와 내비게이션을 확인했다. 이는 아래에 기록한 별도 구형 테스트 전체를 수정한 결과는 아니다.

## 단계와 사용자 결정

| 단계 | 의미와 다음 행동 |
|---|---|
| 의도 `inbox` | 아직 구체화되지 않은 메모·이미지 인박스. 저장하거나 구체화를 요청한다. |
| 구체화 `clarify` | 에이전트가 `brief.md`를 작성한다. 필요한 인터뷰를 마친 뒤 사용자가 방향을 읽고 설계로 넘긴다. |
| 설계 `design` | `spec.md`, `plan.md`, 의존 작업과 변경 범위를 작성한다. 기술 결정도 인터뷰로 묻는다. |
| 승인 대기 `approval` | 사용자가 검토한 문서 버전을 승인하거나 설계 수정을 요청한다. |
| 구현 대기 `queued` | 승인 완료. 일괄 실행 대상으로 접수하기 전에는 실행하지 않는다. |
| 구현 `build` | 의존성과 변경 범위를 확인하고 별도 Git worktree에서 구현·검증·커밋한다. |
| 완료·미확인 `unconfirmed` | 커밋이 프로젝트에 통합되었다. 사용자의 한 번의 결과 확인을 기다린다. |
| 완료 `done` | 사용자가 결과를 확인했다. |

구현 전에는 취소할 수 있다. 구현 중에는 실행을 먼저 중단·완료한다. 완료·미확인 또는 완료에서는 폐기를 요청할 수 있다. 폐기는 `discarding`에서 에이전트가 기록된 커밋을 revert하고 검증한 뒤 `discarded`가 된다. 이미 의존하는 후행 작업은 먼저 취소·폐기하거나 의존성을 정리해야 한다. 이 영향은 요청 전에 화면에 표시하고 실행 시에도 다시 검사한다.

단계별 사용자 결정과 구현 후 폐기는 `work_lifecycle.rs`의 도메인 계약이다. 일반 워크플로우 전이 API로 v2의 승인·완료를 우회할 수 없다. 워크플로우 정의는 순방향 단계와 산출물을 제공하고, 완료 뒤 폐기 같은 결과 처리는 생명주기 기록에 남긴다.

## 승인과 병렬 실행

승인은 의도·구체화·설계·계획의 revision, 의존성, 프로젝트, 저장소, 검증 명령, 프로젝트 디자인에 묶인다. 승인 뒤 이 입력이 바뀌면 재검토해야 한다. 일괄 접수는 선택 전체를 먼저 검증한다. 접수 상태는 디스크에 남고 스케줄러가 우선순위와 생성 순서로 실행한다.

선행 작업이 `unconfirmed` 또는 `done`이면 후행 구현을 시작할 수 있다. 사람이 결과를 확인할 때까지 모든 후행 실행을 멈추지는 않는다. 같은 저장소에서 승인 범위가 겹치는 실행은 순서대로, 독립 범위는 병렬로 실행한다. 저장소 별칭도 Git 공통 디렉터리로 비교한다. 실행 용량이 차면 큐에 남는다.

각 구현은 별도 detached worktree를 사용한다. 실제 변경 경로는 모든 커밋에서 승인 범위와 비교한다. 에이전트는 별도 커밋 승인을 요구하지 않고 관련 변경을 커밋하며 `Sawhorse-Work: <workId>` trailer를 남긴다. 호스트는 전체 해시·범위·출처·깨끗한 worktree를 검증하고 대상 프로젝트에 순차적으로 `cherry-pick -x`한다. 대상 저장소나 브랜치 변경, 사용자 미커밋 변경, 충돌은 통합을 멈추고 오류를 남긴다. 통합 저널과 실제 대상 커밋 해시를 보존하여 중단 후 복구와 폐기의 근거로 쓴다.

## 인터뷰와 A2A 프로토콜

호스트가 실행별로 `runs/protocol/<runId>/`를 제공한다. 에이전트는 고유 ID를 사용해 `<id>.json`을 원자적으로 작성하고 `<id>.reply`를 읽는다. 호스트는 실행 ID와 현재 단계를 결합해 요청을 처리한다.

```json
{"id":"question-1","kind":"question","question":"어느 범위까지 포함할까요?","options":["현재 프로젝트","모든 프로젝트"]}
{"id":"message-1","kind":"message","to":"work-other","text":"공유 파일 변경이 필요합니다. 해당 변경을 양보하고 기다리겠습니다."}
{"id":"complete-1","kind":"complete","dependsOn":[],"scope":["src/feature/"],"commits":[]}
```

질문을 제출한 에이전트는 턴을 끝낸다. 사용자 답변은 작업 상세 패널에서 저장하고 후속 실행으로 이어간다. 미답변 질문이 있으면 다음 단계로 갈 수 없다. A2A 메시지는 같은 프로젝트의 작업 기록에 양방향으로 남는다. 에이전트는 동료의 범위·우선순위·메시지를 읽고 새 충돌을 발견하면 메시지를 보내고 해당 변경을 양보한다. 승인 범위를 넘어선 변경은 호스트도 거절한다. 동적 범위 재협상까지 자동으로 설계를 바꾸지는 않으며 필요한 결정은 인터뷰로 돌린다.

완료 요청은 턴이 끝난 후 처리한다. idle만으로 작업을 완료하지 않는다. 설계에서는 `dependsOn`과 `scope`를 제출한다. 구현·폐기에서는 worktree 기준점 이후의 모든 전체 커밋 해시를 오래된 순서대로 제출한다. `verification.md` 또는 `rollback.md`에는 실제 검증을 설명하는 다음 필드가 필요하다.

```text
result: passed
command: 실제 실행한 검증 명령
exitCode: 0
codeRevision: 마지막 제출 커밋의 전체 SHA
```

호스트는 근거의 형식과 커밋 일치를 검사한다. 에이전트가 실행한 테스트를 독립적으로 재실행하는 CI는 아니므로 기록된 명령·출력과 사용자 결과 확인도 필요하다. 실패나 미검증 상태를 성공 근거로 작성해서는 안 된다.

## 디자인·템플릿·목업

프로젝트 화면에서 디자인/템플릿 라이브러리를 관리한다. 문서 내용을 직접 작성하거나 기존 Markdown·텍스트·HTML·스타일 파일을 불러와 에이전트에 템플릿 또는 DESIGN.md 추출을 요청할 수 있다. 프로젝트 디자인 추출은 기존 DESIGN.md 또는 제한된 양의 CSS/SCSS/Tailwind 설정을 참조한다. 초안을 검토한 뒤 등록하고 프로젝트에 적용한다.

라이브러리는 `.sawhorse/resources/<id>.json`, 할당은 `projects/<id>/resources.json`에 저장한다. 적용한 디자인의 스냅샷은 볼트 `projects/<id>/DESIGN.md`에 저장한다. 라이브러리 변경은 재적용하기 전까지 프로젝트에 영향을 주지 않는다. 할당이 없으면 저장소 루트 DESIGN.md를 읽는다. 내보내기는 선택한 새 `.md` 파일을 만들며 기존 파일을 덮어쓰지 않는다.

템플릿은 이후 생성하는 산출물의 초기 내용으로 적용한다. 원본 의도는 템플릿으로 대체하지 않는다. 기존 산출물과 이력도 유지한다. 목업 갤러리는 최신 버전만 모아 보거나 모든 버전을 탐색하고 이전 버전·피드백·연결 작업을 확인한다. 미리보기 iframe은 스크립트를 실행하지 않는다.

## 검증 범위

Rust 테스트는 단계 결정·인터뷰·승인 무효화·접수 검증·범위/의존성·템플릿/디자인 영속성과 임시 실제 Git 저장소에서 구현 통합 → 사용자 확인 → 의존성 검사 → revert 통합을 확인한다. 브라우저 테스트는 단계별 칸반·질문 답변·승인과 실행 분리·확인·폐기 영향·라이브러리·목업을 확인한다. 브라우저 미리보기는 실제 에이전트를 실행하지 않는다. 실제 CLI와 다중 에이전트 실행의 환경별 검증은 별도로 필요하다.

2026-09-09 검증: 프런트엔드 빌드 성공, Rust 전체 386개 통과·1개 기존 제외, 작업/의도/생명주기/목업/내비게이션 브라우저 검사 34개 통과, 플러그인 검사 35개 통과. 번들 크기 경고는 남아 있다.

추가로 실행한 `product-organization.spec.ts`와 `project-workbench.spec.ts`에서는 14개 검사가 실패했다. 예전 `새 작업`·`프로젝트 범위`·워크플로 캔버스를 찾는 선택자, 커스텀 combobox에 `selectOption`을 호출하는 코드, 변경된 마일스톤/사이드바/문서 가져오기 UI, GitHub 연결 상태 기대값 등이 포함된다. 현재 작업 화면은 별도의 `work-ui.spec.ts`·`design-navigation.spec.ts`로 통과했지만, 이 광범위한 기존 테스트들을 모두 현재 UI에 맞춰 수정하거나 GitHub 연결 문제를 해결한 것은 아니다. 전체 브라우저 회귀 통과로 간주하지 않는다.

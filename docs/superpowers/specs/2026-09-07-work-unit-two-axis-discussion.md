# 작업 단위 설계 논의 기록 — 이슈·개발 투트랙 생명주기

- 날짜: 2026-09-07
- 성격: 설계 논의 기록. 결정 문서가 아니다. 아래는 지금까지 오간 발화의 축약이며,
  새로운 권고나 결론을 덧붙이지 않았다. 판단할 에이전트는 스스로 입장을 세울 것.

## 0. 논의 대상

Sawhorse의 개발 항목(WorkItem)을 이슈와 개발이 하나의 단위로 공유하는 현 구조 —
정확히는 한 레코드에 큐 생명주기(status)와 공정 위치(stage)가 공존하는 2차원 설계 — 가
옳은가에 대한 논의. 사용자는 마지막에 "같은 단위를 투트랙 생명주기로 관리하는 게 이상하다"는
회의감을 명시했다.

## 1. 논의에서 확인한 시스템 사실 (코드 근거)

논의 전제가 되는 현재 구조. 모두 코드로 확인된 사실이다.

1. **단일 저장소.** 이슈·개발 모두 `work/<id>/work.md` 한 건이다
   (`app/src-tauri/src/sdlc.rs` `WorkItem`, `list_work`). 이슈 화면은
   `WorkbenchPage view="issues"`(`app/src/App.tsx`)가 같은 `work` 배열을 받아 렌더링한다.
   이슈 화면 주석: "개발 항목을 요청·승인의 축으로 본 화면. 저장소도 상태 어휘도 board와 같다"
   (`app/src/features/workbench/types.ts`).
2. **두 축이 한 레코드에 공존.** 실행 축: stage/status/priority/workflowInstanceId/decisions.
   이슈 축: issueType(버그·기능·작업·질문)/executionType/labels/assignees/milestone/approve/github*.
   필드 주석: "이슈 축. 별도 저장소가 아니라 같은 개발 항목의 요청·승인·외부 연결 정보다."
3. **status 어휘 8개, 양쪽이 공유.** backlog(백로그) ready(예정) running(진행중) review(검토)
   blocked(보류) done(완료) rejected(반려) cancelled(취소)
   (`types.ts` `STATUSES` / `sdlc.rs` `STATUSES`). blocked는 사이드 상태.
   종료는 3갈래 — 주석: "반려는 요청을 받아들이지 않은 것이고, 취소는 하기로 정한 뒤 그만둔 것.
   둘 다 닫힘이지만 함께 세면 안 된다." `CLOSED_STATUSES`에서 `state: closed`와
   `closed` 날짜가 파생된다(`apply_closure`).
4. **stage = 핀된 워크플로의 현재 노드.** 항목 생성 시 워크플로 정의를
   workflowId/Version/Digest로 고정한다. 기본 워크플로 `sdd-main` v1.1.0 노드:
   intent(의도, Artifact 노드) → design(설계) → build(구현) → test(검증) → deploy(배포).
   각 노드는 입력 artifact role을 요구하고(실행 전 "실질적인 근거" 검사,
   `sdlc_harness.rs`), 전진은 `approved` 이벤트, 후퇴는 `revise` 이벤트다.
   전환마다 `Decision {stage, at, note}`가 기록된다.
5. **학습(maintain) 노드는 제거됨.** v1.1.0에서 종착 노드 maintain을 뺐다. 사유(주석):
   나가는 간선이 없어 순환을 못 만들었고, `learning.md`를 읽는 코드와 실제 파일도 없었다.
   "운영은 끝나는 일이 아니라 기간이라 단계로 두면 항목이 닫히지 않는다."
   배포 후 관찰은 배포 기록 회고 절에 적고 후속 일감은 `dependsOn`으로 잇는다.
   `STAGE_LABELS`에 `maintain: "학습"`이 남아 있는 것은 구버전 워크플로 고정 항목 호환용.
6. **레거시 이관 흔적.** 과거 `이슈/` 폴더의 별도 이슈 노트(IssueNote)를 work 항목으로
   흡수하는 경로가 존재한다: `issue_migration_plan` / `issue_migrate`.
   프로모션 프롬프트는 "새 이슈 노트를 이슈/ 폴더에 만들지 않는다"고 명시한다(jobs.rs).
   GitHub 동기화는 외부 이슈를 work 항목 필드(githubRepo/Number/Url/State)로 미러링한다.
7. **status와 stage의 역할 분담.** status는 큐·교대 신호(running=에이전트 차례,
   review=사람 차례, ready/blocked=대기). stage는 공정 위치. 런 종료는 곧 review이지
   통과가 아니다(프롬프트 주석: "it is not verification passed"). 에이전트는 노드 안에서만
   실행되고 노드 사이 전환은 사람이 승인한다.

## 2. 논의 기록

### 2.1 이슈와 개발은 같은 작업 단위인가

- 질문: 이슈와 개발이 정확히 같은 작업 단위를 다루는가?
- 답변 입장: 같은 단위다. 이슈는 별도 엔티티가 아니라 같은 WorkItem을 요청·승인 축으로
  보는 뷰+필드군이고, 개발(보드)은 같은 항목을 실행·진행 축으로 보는 뷰다.
  근거: 단일 저장소, 같은 status 어휘, 레거시 이관 경로의 존재.
- 별개 단위인 것: 실행 잡(Job/TaskDef, 하네스 런) — "개발 항목과는 다른 개념" 주석 존재.
  GitHub 원본 이슈 — 외부 실체이며 링크 필드로 매핑될 뿐.

### 2.2 같은 단위를 다른 축으로 보는 것이 개발 환경에 도움이 되는가

- 질문: 같은 단위를 것으로 다르게 바라보는 게 도움이 되나?
- 답변 입장(옳다고 봄):
  1. Markdown 볼트엔 조인이 없다. 별도 문서면 상호 참조 무결성을 파일 시스템이
     보장하지 못하고 어긋나면 복구 주체가 사람뿐이다.
  2. 승인→실행 게이트가 한 레코드 안 상태 전이라 원자적이다. 분리 시 "이슈는 승인됐는데
     개발 항목은 ready 아님" 같은 절반 상태가 생긴다.
  3. 프로젝트 내 실험 이력: 분리 운영(레거시 이슈 폴더)을 했고 이관으로 흡수했다.
     이관 경로 존재 자체가 "따로 두면 다시 합친다"는 결과다.
  4. 업계 수렴: GitHub Issues+Projects, Linear, Jira 모두 단일 작업 객체+복수 뷰.
- 같이 인정한 비용: WorkItem 비대화(필드 약 40개, validate가 양축 검사),
  뷰가 필터 책임을 짐, 실행 안 하는 항목(질문 등)도 실행 필드를 달고 생성됨 —
  인박스 승격 게이트가 완충.
- 분리가 이기는 조건: 수명주기가 진짜로 다를 때(지원 티켓 vs 엔지니어링 작업),
  규모·권한 분리가 필요할 때. 현재는 해당 없음.

### 2.3 이슈도 같은 생명주기를 다루는가

- 질문: 이슈도 백로그→예정→진행중→검토→보류→완료를 똑같이 다루는가?
- 답변 입장: 같은 status 어휘를 공유한다. 사용자가 제시한 6단계와 다른 점 두 가지:
  blocked는 순서의 한 칸이 아니라 open 상태 어디든 붙는 사이드 트랙,
  종료는 3갈래(done/rejected/cancelled — 반려와 취소는 다른 사건).
  review에서의 승인(approve)이 ready 진입과 실행 가능으로 이어지는 등
  이슈 축 행위가 status 전이와 결합돼 있다.

### 2.4 개발 화면의 단계(stage)는 무엇인가

- 질문: 개발 화면의 의도·설계·구현·학습 같은 단계는 무엇을 의미하나?
- 답변 입장: stage는 상태와 별개 축으로 "고정된 워크플로의 어느 노드에 서 있는가"다.
  UI의 STAGES 상수는 레거시 폴백이고 실제 노드는 핀된 워크플로가 제공한다.
  노드별 산출 게이트(입력 artifact 실질성 검사), approved/revise 이벤트 전이,
  전환마다 Decision 기록, 노드별 허용 에이전트 역할. 학습 노드는 제거됐고
  라벨만 호환용으로 남아 있다(위 1.5).

### 2.5 이해 확인 — status와 stage의 관계

- 사용자 정리: "이슈는 인간이 관리하는 단계고, 개발의 그것은 시킨 작업이 어떤 단계로
  도는지(프로세스)에 가깝다."
- 답변 입장: 거의 맞다. 정정 한 가지 — stage는 프로세스가 알아서 도는 게 아니라
  모든 공정 사이에 사람 승인이 끼어 있다. 에이전트는 노드 안쪽에서만 실행되고,
  런 종료는 사람 차례 신호(review)다. status="지금 누구 차례인가"의 신호등,
  stage="작업물이 어느 공정에 있나".

### 2.6 GitHub 이슈는 투트랙이 아닌데

- 질문: 깃허브 이슈는 이렇게 투트랙이 아니지 않나?
- 답변 입장: GitHub도 투트랙이다 — 이슈와 PR. 진행 단계는 PR이 가진다
  (draft→review→approved→merged). 이슈는 open/closed뿐이고 나머지는 라벨·프로젝트
  관례다. 매핑: GitHub issue(open/closed)↔status, PR 파이프라인↔stage+워크플로,
  `closes #N`↔참조 없이 같은 문서의 두 필드. GitHub이 이슈 하나로 버틸 수 있었던
  이유는 실행 증거(diff, CI, 리뷰)가 PR 안에 있기 때문이고, sawhorse엔 PR이 없어
  artifact+워크플로가 그 역할을 한다. 라벨 관례는 전이 규칙·무결성이 없어
  에이전트 자동화 게이트로 쓸 수 없다. 워크플로를 1노드로 정의하면 GitHub 이슈
  모델로 퇴화한다 — 일반형이 sawhorse 구조, 특수형이 GitHub 모델.
  판단 질문 제시: 단계 게이트가 제품의 핵심 가치인가?

### 2.7 투트랙 생명주기 자체에 대한 회의감

- 사용자 입장: 같은 단위를 투트랙 생명주기로 관리하는 게 이상하다.
- 답변 입장: 모델 자체는 옳다. 다만 사용자 불편감이 짚는 지점 중 진짜 문제가 두 개
  있다고 인정했다:
  1. 승인 이중화 — 이슈 축 승인(approve 필드, 실행 게이트)과 워크플로 전환 승인
     (approved 이벤트, 노드 게이트)이 개념적으로 겹친다. "검토 승인 = 공정 통과"가
     되어야 하는데 지금은 별개 행위다.
  2. stage 상시 노출 — 원샷 항목도 쓰지 않는 차원의 인지 비용을 낸다.
- 이름 바로잡기: "같은 단위의 투트랙 생명주기"가 아니라 "요청의 생명주기(status) +
  작업의 생명주기(stage)". GitHub에서 기묘하지 않은 이유는 객체가 둘로 나뉘어 있어서고,
  한 파일에 합치면서 보기가 그렇게 된 것. 동류 사례: CI 잡 상태 × 파이프라인 단계,
  k8s Pod phase × 컨테이너 상태.
- 대안 기각 이유: 상태 하나 병합(Jira식)은 status 조합 증식을 부름. stage 제거는
  SDD 게이트 명제 포기.
- 답변에서 제안한 수술 방향(구조 유지 전제): 승인 통합(review 승인 = 전환 승인),
  stage 노출 축소(목록·위젯은 status 단일 어휘, stage는 상세/실행 컨텍스트만),
  기본 워크플로 1~2노드 단순화 허용. 판단 기준으로 "실제 항목 중 게이트 흐름이
  필요한 비율"을 제시 — 답은 아직 나오지 않았다.

## 3. 논의 중 남은 열린 질문

1. 승인 이중화(approve 필드 vs approved 이벤트)를 통합해야 하는가. 통합한다면 어느 쪽 시맨틱으로.
2. stage 노출 범위를 어디까지 줄일 것인가. 목록·위젯·카운트에서 stage를 완전히 뺄 것인가.
3. 기본 워크플로 노드 수. sdd-main 5노드가 기본으로 적절한가, 1~2노드 기본 + 게이트 옵트인이 맞는가.
4. 실제 사용 데이터에서 게이트 흐름(설계 승인 후 구현)을 거치는 항목 비율은 어느 정도인가.
   — 이 수치가 위 세 질문의 판단 기준으로 제시됐으나 아직 측정·답변되지 않았다.

## 4. 이 문서의 한계

- 위 발화는 코드 근거를 인용하지만, 당시 대화에서 파생된 비교·비유(GitHub PR 대응,
  신호등/공정 비유 등)를 포함한다. 코드와 다른 부분이 있으면 코드가 우선한다.
- 결론·결정은 기록하지 않았다. 논의는 사용자의 회의감 제기와 위 열린 질문에서 멈춰 있다.

# 개선 사이클 v2 — 볼트 승인 게이트 + 일괄 처리

`skills/improve` 개편 설계. 확정 후 SKILL.md·design.md·base·템플릿·볼트에 반영한다.

## 왜 고치나

현행 사이클(`미해결 → 설계검토 → 승인 → 적용중 → 해결`)의 구멍은 하나다.
**승인이 채팅 발화만으로 통과된다.** 스킬이 "승인하시겠습니까" 를 묻고 사용자가 "응" 하면
같은 실행에서 노트에 `status: 승인` 을 적고 곧바로 코드를 고친다. 사용자가 설계서를
실제로 읽었다는 근거는 어디에도 없다.

두 번째 문제는 처리량이다. "한 번 실행 = 한 문제 한 단계" 규칙 때문에 13건을 처리하려면
사이클을 13번 돈다. 설계를 여러 개 쌓아두고 한가할 때 몰아 읽고, 승인한 것들을 한 번에
적용하는 흐름이 안 된다.

## 바꾸는 것 요약

| | 현행 | v2 |
|---|---|---|
| 승인 신호 | 채팅 발화 | 볼트 노트의 `approve` 체크박스 (사람만 켤 수 있음) |
| 상태값 | 미해결/설계검토/승인/적용중/해결 | 제안/승인대기/승인/구현중/구현완료 |
| 실행 단위 | 한 문제 한 단계 | 설계 N건 일괄 · 구현 N건 일괄 (단건도 유지) |
| 커밋 시점 | 화면 검증 후 | 단건은 검증 후, **일괄은 문제마다 즉시** |
| 대시보드 | 미해결 1개 뷰 | 제안 / 승인대기 / 구현대기 / 검증대기 |

## 1. 상태 머신

```
        (스킬: 코드 조사 → ## 설계)        (사람: 볼트에서 approve 체크)
제안 ─────────────────────────▶ 승인대기 ─────────────────────────▶ 승인
 ▲                                 ▲ │                                │
 │        (스킬: 설계 개정 시        │ │ (사람: status 를 보류/반려)      │ (스킬: 구현)
 │         approve 자동 해제) ───────┘ ▼                                ▼
 │                                 보류 / 반려                       구현중
 │                                                                    │ (스킬: 경로 한정 커밋 1개)
 └──(사람: 되돌리기 <ID>)◀──── 구현완료 ◀────────────────────────────┘
                                  │
                                  └─(사람: 화면 확인) → verified: 확인
```

| 상태 | 뜻 | 다음에 움직이는 쪽 |
|---|---|---|
| `제안` | 문제만 등록됨. 설계 없음 | 스킬 (`설계`) |
| `승인대기` | 설계 작성 완료. 읽히기를 기다림 | **사람** (볼트에서 체크) |
| `승인` | 사람이 `approve` 를 켬. 구현 권한이 열림 | 스킬 (`구현`) |
| `구현중` | 코드는 고쳤고 커밋 전 | 스킬 (재진입 복구 지점) |
| `부분구현` | 하위 항목 일부만 적용 | 사람 (남은 항목 승격 판단) |
| `구현완료` | 커밋됨 | 사람 (화면 검증) |
| `보류` `반려` | 스캔에서 접힘 | — |

상태값 마이그레이션: `미해결→제안`, `설계검토→승인대기`, `적용중→구현중`, `부분해결→부분구현`,
`해결→구현완료`. `승인`·`보류`·`반려` 는 그대로.

## 2. frontmatter 스키마

```yaml
---
type: 개선
id: FDR-004
screen_id: UI_LDM_FAB-1.1.6.2
screen: 산림재난 위험 검토
url: fdrList.do
category: 버그              # 버그 | UI 개선 | 성능 | 리팩터링
status: 승인대기            # 제안|승인대기|승인|구현중|부분구현|구현완료|보류|반려
approve: false              # ★ 승인 체크박스. 사람만 true 로 만든다
approved: ""                # 스킬이 approve:true 를 처음 관측한 날짜
base: ""                    # 구현 시작 시점 HEAD (일괄이면 배치 시작 HEAD — 배치 식별자 겸용)
branch: improve/fdr
commits: []
verified: 미확인            # 확인 | 부분확인 | 미확인
depends_on: []
dependents: []
related: []
---
```

추가 필드는 `approve` **하나뿐**이다. `base` 의 뜻만 "일괄 구현에서는 배치 시작 시점 HEAD 를
모든 문제에 동일하게 기록" 으로 확장한다 — 같은 `base` 값을 가진 문제 집합이 곧 한 배치이므로
배치 식별용 필드를 따로 만들 필요가 없다.

`.obsidian/types.json` 에 `"approve": "checkbox"` 를 등록한다. 그래야 속성 패널과 Base 표에서
체크박스로 렌더된다.

## 3. 승인 게이트 불변식

이 6개가 이번 개편의 핵심이다. 하나라도 깨지면 v2 는 v1 과 같아진다.

1. **스킬은 `approve` 를 true 로 쓰지 않는다.** false 로 되돌리는 것만 허용된다.
2. 구현 직전 **디스크에서 노트를 다시 읽어** `approve: true` 를 확인한다. 세션 기억이나
   앞선 스캔 결과를 믿지 않는다 (한 세션에서 설계→승인→구현이 이어지는 경우가 특히 위험).
3. 채팅의 "승인해줘" 는 승인이 아니다. 스킬은 체크박스를 대신 켜지 않고, 해당 노트를
   옵시디언으로 열어준 뒤 정지한다. **사용자가 재차 요구해도 마찬가지다** — 이 규칙은
   사용자가 미래의 자신을 구속하려고 스스로 건 것이므로 스킬이 풀어주면 의미가 없다.
   ```powershell
   Start-Process "obsidian://open?vault=기록&file=<URL 인코딩된 볼트 상대경로>"
   ```
4. `approve: true` 인데 `## 설계` 의 `### 변경 대상` 표가 비어 있으면 승인을 무효로 보고 정지한다.
   (설계 없이 체크만 켠 사고 방지)
5. 승인 후 스킬이 설계를 고쳐야 하게 되면 `approve: false` + `status: 승인대기` 로 내리고,
   `## 설계` 끝 `### 개정 이력` 에 날짜와 사유를 적는다. 재승인 없이는 다시 구현하지 않는다.
6. 볼트가 git 저장소이므로 `approve` 플립은 vault backup 커밋에 diff 로 남는다 → 사후 감사 가능.

검증(`verified`)은 게이트가 아니라 사후 기록이므로 채팅으로 갱신해도 된다.
승인만 볼트 전용인 이유는, 승인이 **코드를 고칠 권한을 여는 행위**이기 때문이다.

## 4. 반려 · 수정 요청

설계를 읽고 마음에 안 들 때 사람이 쓰는 경로 두 가지.

| 하는 일 | 스킬의 반응 |
|---|---|
| `## 설계` 아래 `### 검토 의견` 에 한 줄 적는다 | 다음 스캔에서 발견 → 그 문제를 재설계 대상으로 올린다. `승인대기` 유지, 의견 원문은 지우지 않고 그 아래에 대응을 적는다 |
| `status` 를 `보류` / `반려` 로 직접 바꾼다 | 스캔에서 접어 표시. 사유가 적혀 있으면 유지 |

스캔 시 `승인대기` 노트들은 본문까지 읽는다(건수가 적다). `### 검토 의견` 이 있는데
대응 기록이 없으면 그 문제를 우선 제시한다.

## 5. 명령 표면

| 입력 | 동작 |
|---|---|
| (없음) | 스캔 → 상태별 현황 표 → 다음 행동 제안 |
| `등록` / `new` | 문제 등록 · 문제목록에서 승격 (→ `제안`) |
| `설계` | `제안` 상태 전부를 순차 설계 (건수 확인 후 진행) |
| `설계 FDR-004 FDR-006` | 지정 건만 설계 |
| `검토` | `승인대기` 목록 출력 + 옵시디언으로 열고 **정지** |
| `구현` | `승인` 전부를 일괄 구현 |
| `구현 FDR-004` | 단건 구현 (검증 후 커밋 — 현행 방식) |
| `현황` / `status` | 읽기 전용 대시보드 |
| `되돌리기 <ID>` | 단건 revert |
| `되돌리기 배치 <기준커밋>` | 같은 `base` 를 가진 배치를 역순 revert |
| `<ID>` | 그 문제로 진입, 상태에 맞는 단계 1회 |

## 6. 일괄 설계 (`설계`)

순차 실행. 앞 설계가 뒤 설계의 문맥이 되는 것이 이 방식의 값이다.

1. 대상 확정 — `status: 제안` 전부 또는 지정 ID. 건수를 알리고 진행 확인을 받는다.
2. **공통 문맥 1회 로드** — 대상 문제들이 같은 화면이면 진입점(컨트롤러→JSP→JS→매퍼) 지도를
   먼저 만들고 전 건에서 재사용한다. 건마다 같은 파일을 다시 여는 낭비를 없앤다.
3. 문제 루프 — 원인 분석 → 방안 비교 → 선택 → 변경 대상 → (UI 변경이면 목업 HTML + 캡처)
   → 검증 방법 → 되돌리기 영향. 끝나는 즉시 `status: 승인대기`, `approve: false` 로 **건별 저장**.
   중간에 끊겨도 완료분은 디스크에 남는다.
4. **교차 검토 1회** (일괄에만 있는 단계) — 전 건 설계가 끝난 뒤:
   - 변경 대상 파일이 겹치는 문제쌍을 표로 보고한다 → 합칠지 순서를 정할지는 사람이 판단
   - 서로 모순되는 설계(같은 요소를 다르게 바꿈)를 찾아 보고한다
   - 중복 문제(사실상 같은 원인)를 발견하면 통합을 제안한다
5. 보고 — 설계 완료 목록, 겹침·모순 경고, "대시보드 **승인 대기** 표에서 체크" 안내.
   요청하면 승인대기 노트를 옵시디언으로 연다.

UI 목업(현행 1-M)은 그대로 유지한다. 일괄에서는 목업이 더 중요하다 — 사용자가 나중에
혼자 읽고 판단해야 하므로, 글만 있는 설계는 승인 판단이 불가능하다.

## 7. 일괄 구현 (`구현`)

### 7-1. 커밋 시점이 단건과 다른 이유

단건은 지금처럼 **구현 → 화면 검증 → 커밋** 이다. 일괄은 **문제마다 구현 → 즉시 커밋** 으로 바꾼다.
10건을 커밋 없이 쌓으면 한 작업 트리에 10건의 변경이 섞여 **되돌리기 단위가 소멸**한다.
경로 한정 커밋 1개가 이 워크플로우의 유일한 격리 수단이므로, 일괄에서는 커밋을 미룰 수 없다.
따라서 일괄 구현의 결과물은 `status: 구현완료` + `verified: 미확인` 이고,
검증에서 틀린 것이 나오면 `restore` 가 아니라 `git revert` 로 걷어낸다.

### 7-2. 절차

0. **디스크 재스캔** — 대상 = `approve: true` && `status: 승인` && `commits: []`.
   표로 보여주고 최종 확인 1회를 받는다. 개별 승인은 이미 볼트에 있으므로 여기서 다시 묻지 않는다.
1. **사전 점검 1회**
   - `git branch --show-current` ≠ `workBranch` → 중단하고 알린다 (브랜치 전환 금지)
   - `git status --short` 스냅샷 저장. 대상 파일 중 이미 미커밋 수정 상태인 것이 있으면 목록으로 경고 후 확인
   - `git rev-parse --short HEAD` = **배치 기준**. 이 값을 배치 전 문제의 `base` 에 동일하게 기록
2. **실행 순서 결정** (먼저 출력한다)
   - `depends_on` 위상정렬 — 사이클이면 중단하고 보고
   - 변경 대상 파일이 겹치는 문제는 ID 오름차순으로 인접 배치
   - 나머지는 ID 순
3. **문제 루프**
   1. 노트 재확인 (`approve`, `### 변경 대상`)
   2. 앞 문제가 같은 파일을 이미 고쳤으면 그 부분을 다시 읽어 설계 전제가 살아 있는지 본다.
      깨졌으면 **건너뜀** — `status: 승인` 유지, 사유 기록, 사람이 재설계 판단
   3. 구현 — `변경 대상` 파일만. 범위 밖이 필요하면 그 문제는 실패 처리하고 다음으로
   4. `verify` — 컴파일 대상(Java 등)이 바뀐 경우만, `path` 루트에서
   5. 경로 한정 커밋 1개 (`git commit -m "..." -- <파일들>`, 신규 파일만 `git add <파일>` 선행)
   6. 노트 갱신 — `status: 구현완료`, `base`(배치 기준), `commits`, `verified: 미확인`, `## 결과`
   7. 의존성 양방향 기록 (`depends_on` ↔ 상대 노트 `dependents`)
4. **실패·건너뜀 처리** — 실패한 문제만 `git restore -- <그 문제의 변경 대상>` 으로 되돌리고
   `status: 승인` 을 유지한 채 계속 진행한다. 단, **그 파일을 건드리는 후속 문제는 함께 건너뛴다**
   (앞 문제가 빠진 상태에서의 수정은 설계 전제와 다르다).
5. **배치 종료**
   - 컴파일 대상이 하나라도 바뀌었으면 전체 `verify` 1회
   - `개선.md` MOC · 화면별 `문제목록` 의 base 뷰 자산 확인 (표는 뷰가 만든다 — v0.7.0)
   - 배치 리포트 출력:
     ```
     배치 기준 834d238 · 브랜치 improve/fdr
     FDR-004  ✓ a1b2c3d  fdrList.jsp
     FDR-005  ✗ 컴파일 실패 → restore, 승인 유지
     FDR-006  ⊘ 건너뜀 (FDR-005 와 같은 파일)
     FDR-007  ✓ e4f5g6h  fdr.js
     ─────────────────────────────
     성공 2 · 실패 1 · 건너뜀 1
     되돌리기(역순): git revert e4f5g6h a1b2c3d
     ```
   - **통합 검증 체크리스트** — 각 문제의 `검증 방법` 을 화면 단위로 묶어 순서대로 제시한다.
     화면을 한 번 띄워 위에서 아래로 훑을 수 있는 순서여야 한다.
6. **재진입** — 배치가 중간에 끊기면 `구현` 을 다시 실행한다. 커밋된 건은 `구현완료` 라
   대상에서 자동으로 빠지고 남은 `승인` 건부터 이어진다.

### 7-3. 배치 되돌리기

`되돌리기 배치 <기준커밋>` — 같은 `base` 값을 가진 문제들의 `commits` 를 모아
커밋 순서의 **역순**으로 `git revert` 한다. 배치 밖 `dependents` 가 있으면 먼저 알리고 확인받는다.

## 8. 대시보드

`개선.base` 뷰 구성:

| 뷰 | 필터 | 컬럼 |
|---|---|---|
| `제안` | `status == "제안"` | id, 제목, url, category |

## 10. 열린 점

- **Bases 표 안 체크박스 편집** — 설치된 옵시디언 버전에서 실제로 되는지 확인 필요.
  안 되면 노트를 열어 속성 패널에서 체크하는 경로로 갈음한다(설계는 그대로 성립).
- **일괄 설계의 세션 길이** — 10건 이상이면 한 세션에 다 안 들어갈 수 있다. 건별 저장이므로
  재실행하면 남은 `제안` 건부터 이어지지만, 교차 검토(6-4)는 전 건이 끝난 뒤에만 유효하다.
  일괄 설계를 나눠 돌렸으면 마지막에 `설계 검토` 로 교차 검토만 따로 돌릴 수 있게 한다.
- **승인 후 코드가 변한 경우** — 승인과 구현 사이에 다른 사람의 커밋이 들어와 설계 전제가
  깨질 수 있다. 7-2-3-2 의 전제 확인이 같은 배치 안의 앞 문제만 보므로, 배치 시작 시
  `base` 와 각 노트의 설계 작성 시점 사이에 대상 파일이 바뀌었는지도 확인하도록 한다.

## 후속: v0.8.0 — 화면 폴더 폐지 + 중요도 부여

v0.7.0 은 화면(요청 URL)을 **폴더**로 나눴다(`개선/fdrList.do/`). 화면이 하나뿐일 때는 티가 안 났지만 구조적으로 세 가지가 걸린다.

1. **폴더는 한 축으로만 나눈다.** 화면으로 나눠 두면 「미해결을 중요도 순으로」·「인수인계 유래만」 같은 다른 축의 목록은 폴더가 도와주지 못한다. 볼트는 이미 `개념/` 을 평면으로 두고 `domain` 프로퍼티로 나누는 규칙을 갖고 있는데, 개선만 예외였다.
2. **화면마다 `.base` 파일이 복제된다.** 화면이 늘 때마다 뷰 정의 두 벌(`목록` `미해결`)이 복사되고, 뷰를 손보면 전부 따라 고쳐야 한다.
3. `screen_id` · `screen` 두 필드가 사실상 죽어 있었다. 32건 중 `screen_id` 가 채워진 것은 4건, `screen` 은 표기가 제각각(`내부보고서` / `사전검토 상세조회 — 검토상태 (첨부 지도)`)이라 그룹 축으로 못 썼다. (`screen` 은 v0.9.0 에서 그룹 축이 아니라 보고서 열로 되살아난다 — 아래 참조.)

바꾼 것:

| | v0.7.0 | v0.8.0 |
|---|---|---|
| 문제 노트 위치 | `개선/<화면단위>/<ID> ….md` | `개선/<ID> ….md` (평면) |
| 화면 구분 | 폴더 + `screen_id` + `screen` + `url` | `url` 하나 (`screen` 은 v0.9.0 에서 보고용 라벨로 복귀) |
| 화면별 목록 | `<화면단위>.base` 의 `목록` 뷰 | 사업 base 의 `화면별` 뷰 (`groupBy: url`) |
| 인박스 | `문제목록 - <화면단위>.md` (화면마다) | `<idPrefix> 문제목록.md` (사업당 하나) |
| base 범위 | 볼트 / 사업 / 화면 (3) | 볼트 / 사업 (2) |
| 중요도 | 사실상 미사용 | `priority` 를 개선 노트에 **필수**로 부여 |

`priority` 는 원래 볼트 공통 필드이고 `최우선` · `중요` 만 적고 보통이면 비워 두는 규칙이었다. 개선 노트만 `보통` 도 적는 예외를 둔다 — 미해결 문제를 줄 세울 수 있어야 「다음에 뭘 하지」가 답해지기 때문이다. 대신 닫힌 건(`구현완료` · `반려`)은 `보통` 으로 내려 `중요.base` · 대시보드가 끝난 일로 시끄러워지지 않게 한다.

사업 base 에 `미해결`(구현완료·반려 제외, 중요도 순)과 `우선순위별`(`groupBy: priority`) 두 뷰를 더했다. 삭제된 `assets/bases/개선-화면.base` 는 복원하지 않는다.

`vault-hygiene.ps1` 의 `[개선base] … 화면 범위 base 없음` 검사는 `[개선폴더] … 화면단위 하위 폴더 (옛 구조)` 보고로 바뀌었다.

발주처 보고는 개선사항 체크리스트 엑셀 한 장으로 나간다. v0.8.0 스키마만으로는 그 표의 절반이 안 채워져서, 노트에 프로퍼티 5종을 더하고 `screen` 을 되살렸다.

| 항목 | `item` | 새로 추가 |
| 조치내용 | `action` | 새로 추가 (신규 / 수정 / 기존) |
| 완료일(예정일) | `due` | 새로 추가 |
| 비고 | `remark` | 새로 추가 |
| 요구기관 | `origin` 에서 파생 | |
| 검토결과 | `category` 에서 파생 | |
| 우선순위 | `priority` 에서 파생 | 최우선→상 / 중요→중 / 보통→하 |
| 완료여부 | `status` 에서 파생 | |

`screen` 을 되살린 이유는 v0.8.0 이 폐지한 이유와 충돌하지 않는다. 폐지 근거는 「표기가 제각각이라 **그룹 축**으로 못 쓴다」였고, 그룹 축은 지금도 `url` 하나다. `screen` 은 화면 안 어느 영역인지를 사람이 읽는 라벨이고, 보고서에서 `url`(전부 같은 값) 대신 이 칸이 필요했다. 대신 사업 안에서 표기를 통일하는 것이 조건이다.

`priority` 는 v0.8.0 에서 「닫힌 건은 보통으로 내린다」고 했는데, 보고서의 우선순위 열이 그 값을 그대로 쓰므로 **닫힌 건도 원래 중요도를 유지한다.** 끝난 일이 `중요.base` 를 시끄럽게 하는 문제는 그 base 가 `status` 로 거르면 된다.

# 이슈 워크플로

이 스킬은 **요청 → 설계 → 사람 승인 → 실행 → 검증 → 결과**를 남기는 공통 작업 패턴이다. 코드 변경뿐 아니라 문서 작성·조사·협의·결정에도 같은 흐름을 적용한다.

**이슈는 별도의 저장소가 아니다.** 이슈와 개발 항목은 같은 레코드이며, 정본은 `<vault>/work/<id>/` 다. 이슈 화면은 그 레코드를 요청·승인의 축으로 본 화면이고, 개발 칸반은 같은 레코드를 진행 상태의 축으로 본 화면이다. 새 이슈를 `프로젝트/<프로젝트명>/이슈/*.md` 에 만들지 않는다.

세부 데이터 모델은 `${CLAUDE_PLUGIN_ROOT}/packs/si/skills/issues/references/issues-milestones-design.md`를 먼저 읽는다.

## 불변식

1. **한 이슈, 한 레코드.** 배경·근거·설계·승인 대상·결과를 별도 표나 채팅에 분산하지 않고 `work/<id>/` 의 산출물에 남긴다.
2. **사람 승인.** `approvalRequired: true`인 항목은 사용자가 `approve: true`로 바꾸기 전까지 실행하지 않는다. 채팅 발화는 승인이 아니며, 에이전트가 `approve`를 켜지 않는다.
3. **실행 범위.** `spec.md`의 `## 실행 대상`이 비어 있으면 어떤 유형도 실행하지 않는다. 설계가 바뀌면 승인을 해제하고 사유를 남긴다.
4. **유형별 증거.** 코드는 변경 파일·검증·커밋·되돌리기를, 문서는 산출물 경로·검토 결과를, 조사는 근거·답변을, 협의·결정은 회의록·요청·결정 기록을 결과에 남긴다.
5. **상태 하나.** 열림·닫힘(`state`)과 종료일(`closed`)은 `status`에서 앱이 파생한다. 손으로 적지 않는다.
6. **원격 변경 금지.** `github*` 필드는 연결 정보다. GitHub API/CLI 생성·수정·종료·마일스톤 배정, `git push`, SVN 상태 변경은 이 스킬 범위가 아니다.

## 저장 구조

```
<vault>/
  projects/<project-id>/project.md     # 저장소 경로·검증 명령·기본 workflow
  work/<work-id>/
    work.md                            # 상태·승인·유형·마일스톤·GitHub 연결
    intent.md                          # 요청: 배경·원하는 결과·근거
    spec.md                            # 설계: 방안 비교·실행 대상·검증 방법·위험
    verification.md                    # 결과: 적용 내역·증거·남은 일
    plan.md release.md learning.md     # 코드형 SDD workflow 에서만
  calendar/<event-id>.md               # kind: milestone 이 마일스톤이다
```

`work.md`의 `milestone`은 `calendar/`의 마일스톤 일정 ID다. 마일스톤 소속은 이 필드 한 곳에만 적힌다.

## 상태 어휘

개발 항목과 이슈가 같은 어휘를 쓴다. 예전 이슈 노트의 상태는 아래로 읽는다.

| `status` | 표시 | 예전 이슈 노트 |
|---|---|---|
| `backlog` | 백로그 | 제안 / 접수 |
| `review` | 검토 | 승인대기 |
| `ready` | 예정 | 승인 |
| `running` | 진행중 | 진행중 / 부분완료 |
| `blocked` | 보류 | 보류 |
| `done` | 완료 | 완료 |
| `rejected` | 반려 | 반려 |
| `cancelled` | 취소 | 취소 |

`done`·`rejected`·`cancelled`가 `state: closed`다. 반려는 요청을 받아들이지 않은 것이고 취소는 하기로 정한 뒤 그만둔 것이라 한 값으로 접지 않는다.

## 처리 유형

| `executionType` | 설계의 실행 대상 | 결과 증거 |
|---|---|---|
| `코드` | 수정할 파일과 변경 내용 | 검증, 경로 한정 커밋, 되돌리기 |
| `문서` | 작성·갱신할 문서와 독자/기준 | 산출물 링크, 검토 결과 |
| `조사` | 확인할 질문·시스템·자료 | 근거 링크, 답변과 미확인 사항 |
| `협의` | 요청할 상대·안건·기한 | 회의록/회신, 합의 또는 보류 사유 |
| `결정` | 비교할 선택지·결정권자 | 선택 근거, 결정 기록, 후속 이슈 |

기본은 처리 유형과 무관하게 `issue-main` workflow(요청·설계·결과 3종)다. 프로젝트가 `sdd-main`을 고정한 경우에만 6종 산출물을 쓴다. 처리 유형이 바뀌었다고 이미 만든 항목의 workflow를 갈아끼우지 않는다.

## 입력과 절차

모든 실행은 대상 프로젝트의 열린 항목을 중요도와 상태순으로 요약하는 것으로 시작한다.

| 입력 | 하는 일 |
|---|---|
| `등록` / `new` | 대화 내용이나 인박스를 후보로 분류하고, 확인 후 `work/<id>/`를 만들어 `intent.md` 작성 |
| `마일스톤 등록` | 목표·완료 기준·목표일을 받아 `calendar/`에 `kind: milestone` 일정 생성 |
| `분류` | 유형·처리 유형·중복·우선순위·마일스톤 정리. 근거 없는 값은 비움 |
| `설계 [ID...]` | 근거와 실행안을 `spec.md`에 쓰고 `status: review`로 전이 |
| `검토` | 승인 대기 항목을 사람에게 보여 주고 정지 |
| `실행 [ID...]` | 승인된 항목을 유형별로 실행. 코드형은 경로 한정 커밋, 그 외는 산출물·증거 기록 |
| `검증 [ID...]` | 설계의 검증 방법으로 확인하고 `verification.md`와 상태 갱신 |
| `현황` / `status` | 읽기 전용 상태·마일스톤 진행 현황 출력 |
| `이관` | 남아 있는 레거시 이슈 노트를 앱의 이관 기능으로 옮기도록 안내 |

`실행`은 `approve: true`, `status: ready`, `spec.md`의 실행 대상이 모두 충족된 건만 대상으로 한다. 하나가 실패하면 그 항목만 보류하고 다른 독립 항목을 계속할 수 있다. 결과에는 성공·실패·보류와 근거를 건별로 남긴다.

## 설계와 승인

설계할 때 `spec.md`에 다음을 채운다.

1. `## 방안 비교`와 `## 선택`: 대안, 장단점, 선택 이유.
2. `## 실행 대상`: 유형에 맞는 실제 대상과 실행 내용. 비어 있으면 승인해도 실행하지 않는다.
3. `## 검증 방법`, `## 위험 및 되돌리기`: 완료 판단과 실패 대응.

그 뒤 `status: review`, `approve: false`로 저장하고 사람이 승인하도록 안내한다. 검토 의견은 지우지 않고 그 아래에 날짜와 함께 대응을 덧붙인다. 승인 후 설계 변경은 반드시 승인 해제와 재승인을 거친다.

## 코드 실행

`executionType: 코드`면 다음이 추가로 필수다.

- 실행 직전에 디스크에서 `approve: true`와 설계의 파일 범위를 다시 확인한다.
- 대상 프로젝트의 규약을 읽고, 지정된 파일만 수정한다. 범위 밖 파일이 필요하면 멈추고 재설계·재승인한다.
- `git add .`, `git add -A`, `git commit -a`, 브랜치 전환, `git reset --hard`, `git restore .`는 금지한다. 신규 파일도 하나씩 경로를 명시해 추가한다.
- 검증 후 항목별 경로 한정 커밋을 남긴다. 결과에 커밋 SHA·브랜치·검증·`git revert` 순서를 기록한다.
- SVN은 읽기 전용 조회만 허용한다. 원격 push·commit은 하지 않는다.

## 세션 모드 (멀티에이전트)

세션 모드는 **사람이 시작한 협업 세션**이 있을 때만 적용한다. 판단 근거는 lane 프롬프트에 호스트가 내려준 세션 디스크립터뿐이다. **세션 밖에서는 기존 규칙 그대로**다 — 단일 작업 브랜치, 경로 한정 커밋, 산출물 직접 갱신.

세션 안에서는 아래가 브랜치 검사와 갱신 절차를 대체한다. 경로 한정 커밋 같은 나머지 안전 규칙은 자기 worktree 안에서 그대로 적용한다.

1. **디스크립터 검사.** 현재 브랜치를 스스로 판단하지 않는다. 디스크립터가 알려준 worktree 경로와 에이전트 브랜치 `sawhorse/agent/<session-id>/<task-id>`가 실제 상태와 일치하는지 확인하고, 어긋나면 멈추고 보고한다.
2. **노트 intent.** 공유 레코드를 직접 고치지 않는다. 변경은 후보 제안 파일의 `noteIntents` 배열(`notePath`, `expectedLocalHash`, `field`, `value`)로 함께 제출하고, 코어가 검증 뒤 file WAL을 거쳐 한 번만 적용한다.
3. **후보 제출.** 후보는 lane 프롬프트가 알려준 인박스 경로에 아래 요청 파일을 써서만 제출한다. 가능한 lint·typecheck·테스트는 자기 worktree에서 돌리고 결과를 `checks`에 담는다. 대표 체크아웃은 만지지 않으며, 병합은 사람 승인 후 앱이 수행한다.
4. **rebase 금지.** 통합 브랜치는 rebase하지 않는다. 격리 브랜치의 promotion은 승인된 merge 또는 PR 게시로만 처리한다.

```json
{
  "op": "propose",
  "sessionId": "s-20260905-a1b2",
  "taskId": "ui-shell",
  "agent": "claude-code",
  "worktree": "/local/path/to/worktree",
  "baseSha": "0123456...",
  "sourceSha": "abcdef0...",
  "summary": "변경 요약",
  "checks": [{ "name": "typecheck", "status": "passed" }],
  "noteIntents": [
    { "notePath": "work/<work-id>/work.md", "expectedLocalHash": "<로컬 해시>", "field": "<필드>", "value": "<새 값>" }
  ]
}
```

제출 전 자기 worktree는 clean이어야 한다(모든 변경이 커밋된 상태). amend·추가 커밋은 같은 후보의 수정이 아니라 새 후보다 — 이전 후보는 `superseded`가 된다.

## 마일스톤

마일스톤에는 목표·완료 기준·목표일을 적는다. 진행률은 구성 항목의 `state: closed` 비율이며 손으로 적지 않는다. 마일스톤을 닫기 전에는 열린 항목·검증 미완료 항목을 보고하고, 예외가 있다면 근거를 남긴다. 마일스톤에 항목이 남아 있는 동안 앱은 그 일정의 삭제와 일반 일정으로의 변경을 거절한다.

## 레거시 이슈 노트

이름을 바꾸기 전 볼트에는 `사업/<이름>/이슈/*.md`(또는 `개선/`)가 남아 있을 수 있다. 이 노트들은 **읽기 전용 입력**이다.

- 새 작업을 그 폴더에 만들지 않는다.
- 옮길 때는 앱의 이슈 화면 하단 「이관하지 않은 이슈 노트」를 쓰도록 안내한다. 이관은 `work/<id>/`를 만들고 원본에는 `migrated_to` 표시만 남기므로 되돌릴 수 있다.
- 손으로 옮길 때도 원본을 지우거나 이동하지 않는다.

## 호환과 역할 분리

- `/sawhorse:improve`는 **코드형 레거시 이슈의 호환 별칭**이다. 새 작업은 이 스킬을 정본으로 사용한다.
- `daily-log`, `codebase-docs`, 회의 기록 등에서 생긴 후속 작업은 바로 확정하지 않고 후보로 모은다. `등록`/`분류`에서 중복·범위·처리 유형을 판단한다.
- `improve-excel`은 보고용 내보내기일 뿐, 상태의 정본이 아니다.

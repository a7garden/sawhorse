# 이슈 워크플로

이 스킬은 **요청 → 설계 → 사람 승인 → 실행 → 검증 → 결과**를 Markdown 이슈 노트 한 장에 남기는 공통 작업 패턴이다. 코드 변경뿐 아니라 문서 작성·조사·협의·결정에도 같은 흐름을 적용한다.

세부 데이터 모델은 `${CLAUDE_PLUGIN_ROOT}/packs/si/skills/issues/references/issues-milestones-design.md`를 먼저 읽는다. 레거시 `개선`은 호환 입력일 뿐이며, 새 산출물은 항상 이 문서의 이슈 규격을 사용한다.

## 불변식

1. **한 이슈, 한 기록.** 배경·근거·설계·승인 대상·결과를 별도 표나 채팅에 분산하지 않고 `<ID> <제목>.md`에 남긴다.
2. **사람 승인.** `approval_required: true`인 이슈는 사용자가 볼트에서 `approve: true`를 켜기 전까지 실행하지 않는다. 채팅 발화는 승인이 아니다.
3. **실행 범위.** `## 설계 > ### 실행 대상`이 비어 있으면 어떤 유형도 실행하지 않는다. 설계가 바뀌면 `approve: false`, `status: 승인대기`로 되돌리고 `### 개정 이력`에 사유를 남긴다.
4. **유형별 증거.** 코드 이슈는 변경 파일·검증·커밋·되돌리기를, 문서 이슈는 산출물 경로·검토 결과를, 조사 이슈는 근거·답변을, 협의·결정 이슈는 회의록·요청·결정 기록을 결과에 남긴다.
5. **닫힘 정합성.** 새 이슈는 `완료|취소`일 때만 `state: closed` 및 `closed: YYYY-MM-DD`다. 그 외 상태는 `state: open`이다.
6. **원격 변경 금지.** GitHub 필드는 연결 정보다. GitHub API/CLI 생성·수정·종료·마일스톤 배정, `git push`, SVN 상태 변경은 이 스킬 범위가 아니다.

## 이슈 구조

```
사업/<사업명>/
  이슈/
    이슈.md
    <idPrefix> 이슈.base
    <idPrefix> 이슈목록.md
    <ID> <제목>.md
  마일스톤/
    마일스톤.md
    <ID> <제목>.md
```

- 새 이슈는 `템플릿/이슈.md`, 마일스톤은 `템플릿/마일스톤.md`로 만든다.
- 이슈 ID는 사업 안에서 단조 증가한다. 마일스톤 ID는 `<idPrefix>-M1`처럼 사업 안에서 유일해야 한다.
- 이슈는 하나의 `milestone`만 가질 수 있다. 값이 있으면 같은 사업 `마일스톤/`의 실제 ID여야 한다.
- 목록은 Base 뷰가 만든다. 이슈·마일스톤 상태를 MOC의 Markdown 표로 복제하지 않는다.

## 실행 유형

| `execution_type` | 설계의 실행 대상 | 결과 증거 |
|---|---|---|
| `코드` | 수정할 파일과 변경 내용 | 검증, 경로 한정 커밋, 되돌리기 |
| `문서` | 작성·갱신할 문서와 독자/기준 | 산출물 링크, 검토 결과 |
| `조사` | 확인할 질문·시스템·자료 | 근거 링크, 답변과 미확인 사항 |
| `협의` | 요청할 상대·안건·기한 | 회의록/회신, 합의 또는 보류 사유 |
| `결정` | 비교할 선택지·결정권자 | 선택 근거, 결정 기록, 후속 이슈 |

모든 유형이 `제안 → 승인대기 → 승인 → 진행중 → 완료`를 기본으로 한다. `부분완료`, `보류`, `취소`는 예외 상태다. `코드`의 구현 안전 규칙은 아래 「코드 실행」을 추가 적용한다.

## 입력과 절차

모든 실행은 대상 사업의 이슈·마일스톤·레거시 개선 노트를 스캔하고, 열린 이슈를 중요도와 상태순으로 요약하는 것으로 시작한다.

| 입력 | 하는 일 |
|---|---|
| `등록` / `new` | 이슈목록 인박스 또는 대화 내용을 이슈 후보로 분류하고, 확인 후 새 이슈 노트 생성 |
| `마일스톤 등록` | 목표·완료 기준·목표일을 받아 마일스톤 노트 생성 |
| `분류` | 제안 이슈의 유형·실행 유형·중복·우선순위·마일스톤을 정리. 근거 없는 값은 비움 |
| `설계 [ID...]` | 제안 이슈의 근거와 실행안을 작성하고 `승인대기`로 전이 |
| `검토` | 승인대기 이슈를 열어 사람이 승인하거나 검토 의견을 남기게 한 뒤 정지 |
| `실행 [ID...]` | 승인된 이슈를 유형별로 실행. 코드형은 경로 한정 커밋, 비코드형은 산출물·증거 기록 |
| `검증 [ID...]` | 설계의 검증 방법으로 확인하고 `완료` 또는 `부분완료`로 갱신 |
| `현황` / `status` | 읽기 전용 상태·마일스톤 진행 현황 출력 |
| `이관` | 레거시 개선 노트의 변환 미리보기 후, 사용자 승인 뒤에만 이슈로 복제·링크 갱신 |

`실행`은 `approve: true`, `status: 승인`, `### 실행 대상`이 모두 충족된 건만 대상으로 한다. 하나가 실패하면 그 이슈만 보류하고 다른 독립 이슈를 계속할 수 있다. 결과에는 성공·실패·보류와 근거를 건별로 남긴다.

## 설계와 승인

설계할 때 다음을 이슈 노트에 채운다.

1. `## 근거 및 분석`: 코드·문서·회의·요청 등 확인 가능한 근거와 추정을 구분한다.
2. `### 방안 비교`와 `### 선택`: 대안, 장단점, 선택 이유를 남긴다.
3. `### 실행 대상`: 유형에 맞는 실제 대상과 실행 내용을 표로 적는다.
4. `### 검증 방법`, `### 위험 및 되돌리기`: 완료 판단과 실패 대응을 적는다.
5. `status: 승인대기`, `approve: false`, `state: open`으로 저장하고 사람이 볼트에서 승인하도록 안내한다.

`### 검토 의견`은 지우지 않는다. 대응은 의견 아래에 날짜와 함께 덧붙인다. 승인 후 설계 변경은 반드시 승인 해제와 재승인을 거친다.

## 코드 실행

`execution_type: 코드`면 다음이 추가로 필수다.

- 실행 직전에 디스크에서 `approve: true`와 설계의 파일 범위를 다시 확인한다.
- 대상 프로젝트의 규약을 읽고, 지정된 파일만 수정한다. 범위 밖 파일이 필요하면 멈추고 재설계·재승인한다.
- `git add .`, `git add -A`, `git commit -a`, 브랜치 전환, `git reset --hard`, `git restore .`는 금지한다. 신규 파일도 하나씩 경로를 명시해 추가한다.
- 검증 후 이슈별 경로 한정 커밋을 남긴다. 결과에 커밋 SHA·브랜치·검증·`git revert` 순서를 기록한다.
- SVN은 읽기 전용 조회만 허용한다. 원격 push·commit은 하지 않는다.

## 세션 모드 (멀티에이전트)

세션 모드는 **사람이 시작한 협업 세션**이 있을 때만 적용한다. 판단 근거는 lane 프롬프트에 호스트가 내려준 세션 디스크립터뿐이다. **세션 밖에서는 기존 규칙 그대로**다 — 단일 `workBranch`, 경로 한정 커밋, 이슈 노트 직접 갱신을 앞 절 규칙대로 수행한다.

세션 안에서는 아래가 브랜치 검사와 노트 갱신 절차를 대체한다. 경로 한정 커밋 같은 나머지 안전 규칙은 자기 worktree 안에서 그대로 적용한다.

1. **디스크립터 검사.** 현재 브랜치가 `workBranch`와 같은지 검사하지 않는다. 대신 디스크립터가 알려준 worktree 경로와 에이전트 브랜치 `sawhorse/agent/<session-id>/<task-id>`가 실제 worktree·브랜치 상태와 일치하는지 확인하고, 어긋나면 멈추고 보고한다. 기존 `workBranch`는 통합 브랜치의 호환 입력값으로 읽는다.
2. **노트 intent.** 공유 이슈 노트를 직접 고치지 않는다. 노트 변경은 후보 제안 파일의 `noteIntents` 배열(`notePath`, `expectedLocalHash`, `field`, `value`)로 함께 제출하고, 코어가 검증 뒤 file WAL을 거쳐 한 번만 적용한다.
3. **후보 제출.** 후보는 lane 프롬프트가 알려준 인박스 경로에 아래 요청 파일을 써서만 제출한다. 가능한 lint·typecheck·테스트는 자기 worktree에서 돌리고 결과를 `checks`에 담는다. 대표 체크아웃은 만지지 않으며, 병합은 사람 승인 후 앱이 수행한다.
4. **rebase 금지.** 통합 브랜치는 rebase하지 않는다. 격리 브랜치의 promotion은 승인된 merge 또는 PR 게시로만 처리한다.

```json
{
  "op": "propose",
  "sessionId": "s-20260905-a1b2",
  "taskId": "ui-shell",
  "agent": "claude-code",
  "worktree": "/local/path/to/worktree",
  "baseSha": "0123456...",
  "sourceSha": "abcdef0...",
  "summary": "변경 요약",
  "checks": [{ "name": "typecheck", "status": "passed" }],
  "noteIntents": [
    { "notePath": "사업/<사업명>/이슈/<ID> <제목>.md", "expectedLocalHash": "<노트 로컬 해시>", "field": "<필드>", "value": "<새 값>" }
  ]
}
```

제출 전 자기 worktree는 clean이어야 한다(모든 변경이 커밋된 상태). amend·추가 커밋은 같은 후보의 수정이 아니라 새 후보다 — 이전 후보는 `superseded`가 된다.

### 세션 노트 필드

| 필드 | 세션 모드에서의 의미 |
|---|---|
| `approve` | 기존 의미 유지 — 이슈 설계·실행 권한. 병합 승인과 별개 |
| `base` | 세션의 `target_start_sha` |
| `branch` | 통합 대상 branch |
| `commits` | 기존 의미 유지 — 후보를 구성한 구현 commit |
| `verified` | 기존 문자열 `확인\|부분확인\|미확인` 유지 — 대표 체크아웃 검증 뒤 갱신 |
| `integration_commits` | (신규) 통합 체크아웃에 생긴 merge commit과 후보 연결 |
| `integration_reverts` | (신규) 실패 후보를 제거한 revert commit |
| `session_id`·`candidate_ids` | (신규) 세션·후보 감사 연결 |

## 마일스톤

마일스톤에는 목표·완료 기준·목표일을 적는다. 이슈의 상태를 손으로 표로 옮기지 말고 사업 이슈 Base의 `마일스톤별` 뷰를 임베드한다. 마일스톤을 `완료`로 닫기 전에는 열린 이슈·부분완료 이슈·검증 미완료 이슈를 보고하고, 예외가 있다면 `## 메모`에 근거를 남긴다.

## 호환과 역할 분리

- `/sawhorse:improve`는 **코드형 레거시 이슈의 호환 별칭**이다. 새 이슈를 만들거나 관리할 때는 이 스킬을 정본으로 사용한다.
- `daily-log`, `codebase-docs`, 회의 기록 등에서 생긴 후속 작업은 이슈를 바로 확정하지 않고 이슈목록의 후보로 모은다. `등록`/`분류`에서 중복·범위·실행 유형을 판단한다.
- `improve-excel`은 이슈의 보고용 내보내기일 뿐, 이슈 상태의 정본이 아니다.

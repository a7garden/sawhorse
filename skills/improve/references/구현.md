# 구현 (`승인` → `구현완료`) · 되돌리기

`improve` 스킬의 구현 경로 상세. **SKILL.md 의 안전 규칙·승인 게이트·금지사항이 전제다** — 어긋나 보이면 SKILL.md 가 우선.

시작하기 전 반드시:

- 디스크에서 노트를 **다시 읽어** `approve: true` 를 확인한다 (승인 게이트 2). 세션 기억을 믿지 않는다.
- `### 변경 대상` 이 비어 있으면 승인 무효로 보고 정지한다 (승인 게이트 4).
- `approved` 가 비어 있으면 오늘 날짜를 기록하고 `status: 승인` 으로 맞춘다.

## 2. 단건 구현 (`구현 <ID>`)

### 재진입 복구

`구현중` 상태로 들어온 경우(이전 세션이 검증 요청에서 멈춤) 아래를 먼저 확인하고 분기한다. 확인 없이 구현을 다시 시작하지 않는다.

| 확인 | 상황 | 조치 |
|---|---|---|
| 노트의 `commits` 가 비어 있지 않다 | 이미 커밋됨 | 절차 3-2(의존성)부터 이어간다 |
| `git log --grep` 으로 이 ID 의 커밋이 잡힌다 | 커밋됐는데 노트 미갱신 | 절차 3-2 부터 이어가고 노트를 맞춘다 |
| 변경 대상이 수정 상태로 남아 있다 | 구현은 끝났고 검증 대기 | 검증 방법을 다시 제시하고 정지 |
| 변경이 없다 | 구현이 유실·폐기됨 | 사용자에게 알리고 상태를 `승인` 으로 되돌린 뒤 구현부터 다시 한다 |

### 절차

1. **사전 점검** — `git status --short`, `git branch --show-current`, `git rev-parse --short HEAD` 로 현재 상태를 기록한다.
   - 현재 브랜치가 `workBranch` 인지 확인한다. **다르면 멈추고 사용자에게 알린다.** 브랜치를 임의로 전환하지 않는다.
   - `branch`(=`workBranch`)와 `base`(HEAD) 를 문제 노트에 기록하고 `status: 구현중` 으로 바꾼다.
   - 미커밋 변경은 **그대로 둔다**. 사용자의 진행 중 작업이므로 `stash`·`checkout`·`reset` 으로 건드리지 않는다.
   - 변경 대상 파일이 이미 미커밋 수정 상태이면 경고한다: "이 파일에는 기존 미커밋 변경이 있어 커밋 시 그 변경도 함께 들어갑니다. 계속할까요?" 확인 없이는 진행하지 않는다.
2. **구현** — 설계의 `변경 대상` 파일만 수정한다. 범위 밖이 필요하면 멈추고 보고한다.
3. **검증**
   - `verify` 명령이 있고 컴파일 대상(Java 등)이 바뀌었으면 **`path` 루트에서** 실행한다. 실패하면 커밋하지 않고 원인을 보고한다(상태는 `구현중` 유지).
   - JSP/JS/CSS 처럼 컴파일로 확인되지 않는 변경은 설계의 `검증 방법` 을 사용자에게 그대로 제시하고 **정지**한다. 상태는 `구현중`.
   - 사용자가 확인 없이 커밋을 지시하면 진행하되 `verified: 미확인` 으로 기록한다.
4. **커밋 및 결과** — 아래 절차 3.
5. **구현 폐기** (검증에서 기능이 틀린 것으로 판명되고 사용자가 폐기를 지시한 경우)
   - `git restore -- <설계의 변경 대상 파일>` 로 **그 경로만** 되돌린다. 신규 생성했다 스테이징한 파일은 `git restore --staged -- <파일>` 후 파일을 지운다. 사용자의 다른 미커밋 작업은 건드리지 않는다.
   - `status: 승인대기`, `approve: false`, `approved: ""` 로 내리고 `### 개정 이력` 에 폐기 사유와 날짜를 남긴다.
   - 재설계가 필요하면 `references/설계.md` 로 간다. 재승인은 다시 볼트에서 받는다.

## 2-B. 일괄 구현 (`구현`)

### 왜 커밋 시점이 단건과 다른가

단건은 **구현 → 화면 검증 → 커밋** 이다. 일괄은 **문제마다 구현 → 즉시 커밋** 이다.
여러 건을 커밋 없이 쌓으면 한 작업 트리에 변경이 섞여 **되돌리기 단위가 소멸**한다.
경로 한정 커밋 1개가 이 워크플로우의 유일한 격리 수단이므로, 일괄에서는 커밋을 미룰 수 없다.
따라서 일괄 구현의 결과물은 `status: 구현완료` + `verified: 미확인` 이고, 검증에서 틀린 것이 나오면
`restore` 가 아니라 `git revert` 로 걷어낸다.

### 절차

0. **디스크 재스캔** — 대상 = `approve: true` && `status: 승인` && `commits: []`.
   `### 변경 대상` 이 비어 있는 건은 승인 무효로 제외하고 보고한다.
   대상을 표로 보여주고 최종 확인 1회를 받는다. 개별 승인은 이미 볼트에 있으므로 건별로 다시 묻지 않는다.
1. **사전 점검 1회**
   - `git branch --show-current` ≠ `workBranch` → 중단하고 알린다.
   - `git status --short` 스냅샷을 기록한다. 대상 파일 중 이미 미커밋 수정 상태인 것이 있으면 목록으로 경고하고 확인받는다.
   - `git rev-parse --short HEAD` = **배치 기준**. 이 값을 배치 전 문제의 `base` 에 **동일하게** 기록한다 — 같은 `base` 값이 곧 한 배치의 식별자다.
2. **실행 순서 결정** (먼저 출력한다)
   - `depends_on` 위상정렬. 사이클이면 중단하고 보고한다.
   - 변경 대상 파일이 겹치는 문제는 ID 오름차순으로 인접 배치한다.
   - 나머지는 ID 순.
3. **문제 루프** — 각 문제마다:
   1. 노트를 다시 읽어 `approve: true` 와 `### 변경 대상` 을 확인한다.
   2. 대상 파일이 **설계 작성 이후에 바뀌었는지** 본다. 배치 안의 앞 문제가 고쳤거나(같은 파일), `base` 이전에 남이 고쳤을 수 있다. 설계 전제가 깨졌으면 **건너뜀** — `status: 승인` 유지, 사유 기록, 재설계 판단은 사람 몫.
   3. `status: 구현중` 으로 바꾸고 `변경 대상` 파일만 수정한다. 범위 밖 파일이 필요해지면 그 문제는 **실패** 처리하고 다음으로 간다.
   4. `verify` — 컴파일 대상이 바뀐 경우만, `path` 루트에서.
   5. 경로 한정 커밋 1개 (절차 3-1).
   6. 노트 갱신 — `status: 구현완료`, `base`(배치 기준), `commits`, `verified: 미확인`, `## 결과` 작성.
   7. 의존성 양방향 기록 (절차 3-2).
4. **실패·건너뜀 처리** — 실패한 문제만 `git restore -- <그 문제의 변경 대상>` 으로 되돌리고 `status: 승인` 을 유지한 채 **배치를 계속 진행**한다.
   단, **그 파일을 건드리는 후속 문제는 함께 건너뛴다** — 앞 문제가 빠진 상태에서의 수정은 설계 전제와 다르다.
5. **배치 종료**
   - 컴파일 대상이 하나라도 바뀌었으면 전체 `verify` 1회.
   - SKILL.md 의 「전파」에 따라 `개선.md` MOC(상태 표 + `## 구현 배치`)와 화면별 `문제목록` 인덱스를 갱신한다.
   - **배치 리포트** 출력:

     ```
     배치 기준 834d238 · 브랜치 improve/fdr
     FDR-004  ✓ a1b2c3d  fdrList.jsp
     FDR-005  ✗ 컴파일 실패 → restore, 승인 유지
     FDR-006  ⊘ 건너뜀 (FDR-005 와 같은 파일)
     FDR-007  ✓ e4f5g6h  fdr.js
     ─────────────────────────────
     성공 2 · 실패 1 · 건너뜀 1
     되돌리기(역순): git revert e4f5g6h a1b2c3d
     ```

   - **통합 검증 체크리스트** — 각 문제의 `검증 방법` 을 화면 단위로 묶어 순서대로 제시한다. 화면을 한 번 띄워 위에서 아래로 훑을 수 있는 순서여야 한다.
   - 원격·SVN 반영은 사용자가 수동으로 판단한다는 점을 덧붙인다(SVN 작업복사본에는 이 변경이 로컬 수정으로 보인다).
6. **재진입** — 배치가 중간에 끊기면 `구현` 을 다시 실행한다. 커밋된 건은 `구현완료` 라 대상에서 자동으로 빠지고 남은 `승인` 건부터 이어진다.

## 3. 커밋 및 결과

1. **커밋** — 변경 파일을 명시해 한 번에 커밋한다. 원칙은 문제당 커밋 1개다.

   ```
   git add <신규 파일 경로>            # 신규 파일이 있을 때만. 파일 하나씩 명시
   git commit -m "<메시지>" -- <file1> <file2>
   ```

   신규 파일을 `git add` 하지 않으면 경로 한정 커밋이 `error: pathspec ... did not match any file(s) known to git` 로 거부한다. 반대로 디렉터리나 `.` 을 add 하면 무관한 파일이 딸려 들어간다 — 파일 경로를 하나씩 적는다.

   메시지 규격:

   ```
   fix(FDR-001): 상태 저장 시 하단 내부보고서 입력값 초기화 수정

   문제: 사업/<사업명>/개선/fdrList.do/FDR-001 상태 저장 시 하단 폼 초기화
   설계: 2번안 — fdrReport.jsp 를 분할해 part 별 부분 렌더링
   ```

   앞의 타입은 `category` 에 맞춘다(`버그`→`fix`, `UI 개선`→`feat` 또는 `style`, `성능`→`perf`, `리팩터링`→`refactor`).
   커밋 후 브랜치를 옮기거나 병합하지 않는다.
2. **의존성 판정** — 이번에 건드린 파일을 이전 개선 커밋이 건드린 적 있는지 확인한다:

   ```
   git log --oneline -F --grep="<idPrefix>-" -- <변경 파일들>
   ```

   `-F`(고정 문자열)를 반드시 붙인다. `--grep="(<idPrefix>-"` 처럼 괄호를 정규식으로 넘기면 `grep.patternType=extended` 환경에서 `fatal: Unmatched ( or \(` 로 죽는다.

   겹치는 선행 문제가 있으면 이번 노트의 `depends_on` 에 그 ID 를, **그 노트의 `dependents` 에 이번 ID 를** 넣는다. 양방향 기록은 필수다 — 어느 쪽 문서를 열어도 되돌리기 순서를 알 수 있어야 한다.
3. **`## 결과` 작성**

   ```markdown
   ### 적용 내역
   | 항목 | 값 |
   |---|---|
   | 커밋 | `a1b2c3d` |
   | 브랜치 | `improve/fdr` |
   | 기준 | `834d238` |
   | 검증 | 확인 — 내부보고서 화면에서 상태 저장 후 하단 입력값 유지 확인 |

   ### 변경 파일
   | 파일 | 변경 내용 |

   ### 되돌리기
   `git revert a1b2c3d`

   - 선행 의존: FDR-002 — 이 수정보다 먼저 되돌리면 안 됨
   - 후행 영향: FDR-005 가 이 커밋 위에 쌓여 있음 — 먼저 되돌릴 것
   - 이후 같은 파일을 건드린 커밋: (있으면 나열하고 충돌 가능성 명시)
   ```

4. **전파** — SKILL.md 의 「전파」 절차를 따른다. `개선.md` 의 `## 구현 배치` 는 노트의 `base` 값으로 묶어 만든다:

   | 배치 기준 | 문제 | 커밋 | 되돌리기 |
   |---|---|---|---|
   | `834d238` | FDR-004, FDR-007 | `a1b2c3d` `e4f5g6h` | `git revert e4f5g6h a1b2c3d` |

5. **보고** — 커밋 ID, 변경 파일, 되돌리기 명령, 의존성, 남은 미구현 건수.

## 4. 되돌리기

### 4-A. 단건 (`되돌리기 <ID>`)

1. 문제 노트에서 `commits` 와 `dependents` 를 읽는다.
2. `dependents` 가 비어 있지 않으면 **먼저 후행 문제를 되돌려야 한다**고 알리고 순서를 제시한 뒤 확인을 받는다.
3. `git log --oneline <커밋>.. -- <변경 파일>` 로 이후 같은 파일을 건드린 커밋을 확인해 충돌 가능성을 미리 보고한다.
4. `git revert <커밋>` 을 실행한다. 메시지에 문제 ID 를 남긴다. 충돌이 나면 자동 해결하지 않고 멈춰서 상태를 보고한다.
5. 문제 노트를 `status: 제안`, `approve: false`, `approved: ""`, `commits: []` 로 되돌리고 `## 결과` 에 되돌린 사실·revert 커밋 ID·사유를 **추가**한다(기존 내역은 지우지 않는다). 목록·MOC 도 갱신한다.

### 4-B. 배치 (`되돌리기 배치 <기준커밋>`)

1. `base` 가 그 기준커밋인 문제를 모두 모은다. 목록과 커밋을 표로 보여주고 확인받는다.
2. 배치 **밖**에 `dependents` 가 있으면 먼저 알리고, 그것부터 되돌릴지 판단을 받는다.
3. 커밋 순서의 **역순**으로 `git revert` 한다. 충돌이 나면 그 지점에서 멈추고 보고한다.
4. 각 노트를 4-A 의 5번과 같이 되돌리고 `개선.md` 의 `## 구현 배치` 에 되돌림 사실을 적는다.

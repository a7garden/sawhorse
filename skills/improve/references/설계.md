# 설계 (`제안` → `승인대기`)

`improve` 스킬의 설계 경로 상세. **SKILL.md 의 안전 규칙·승인 게이트·금지사항이 전제다** — 어긋나 보이면 SKILL.md 가 우선.

이 단계에서 **코드는 한 줄도 바꾸지 않는다.** 코드베이스는 읽기 전용으로만 본다.

## 1. 한 문제 설계하기

단건이든 일괄이든 한 문제를 설계하는 방법은 같다. 일괄은 이 루프를 순차로 돌고 끝에 교차 검토를 붙인다.

1. 코드베이스를 **읽기 전용**으로 조사한다. 문제 노트의 화면 ID·URL 로 진입점(컨트롤러 → 뷰 → JS → 매퍼)을 추적한다.
2. `## 원인 분석` 을 근거와 함께 확정한다. 모든 주장 옆에 `파일:행` 을 적는다. 확인하지 못한 추정은 "추정" 이라고 명시한다.
3. `## 설계` 를 아래 구조로 쓴다:

   ```markdown
   ### 방안 비교
   | 안 | 내용 | 장점 | 단점 | 영향 범위 |

   ### 선택
   <채택안과 이유. 사용자 제안과 다르면 무엇이 어떻게 다른지 먼저 밝힌다.>

   ### 변경 대상
   | 파일 | 변경 내용 |

   ### 목업
   <화면이 바뀌는 문제만. 안별 캡처 임베드 + 목업 HTML 링크. 아래 1-M 참조. 해당 없으면 이 절을 지운다.>

   ### 검증 방법
   <어떤 화면에서 무엇을 눌러 무엇이 보이면 성공인지>

   <!-- 목업이 있으면: 목업과 실제 화면이 어디까지 일치해야 하는지도 여기에 적는다 -->

   ### 되돌리기 영향
   <이 수정을 되돌릴 때 같이 깨지는 것 / 선행 의존>

   ### 검토 의견
   <사용자가 승인 전에 적는 자리. 스킬은 비워둔 채로 남긴다.>
   ```

   `### 변경 대상` 이 비면 승인해도 구현되지 않는다(승인 게이트 4). 파일을 특정하지 못했으면 설계가 아직 안 끝난 것이다.
4. `변경 대상` 이 프로젝트 `CLAUDE.md` 의 허용 범위를 벗어나면 그 사실을 설계에 적고 대안(전용 파일 신규 생성 등)을 제시한다.
5. **화면이 바뀌는 문제는 목업을 먼저 만든다** (아래 1-M). 글로만 쓴 설계로 UI 승인을 받지 않는다.
6. `status: 승인대기`, `approve: false` 로 저장한다.
7. 단건이면 채택안 요약 + 변경 파일 수 + 위험을 3~5줄로 보고하고, **승인은 볼트에서 체크해야 한다**고 알린 뒤 정지한다.

### 재설계 (`### 검토 의견` 이 달린 경우)

사용자가 승인 대신 의견을 적었으면 그 지적을 출발점으로 설계를 고친다.

- **의견 원문을 지우지 않는다.** 그 아래에 `> 대응 (YYYY-MM-DD): …` 로 무엇을 어떻게 바꿨는지 적는다.
- 상태는 `승인대기` 그대로 두고 `approve` 는 `false` 를 유지한다.
- 지적을 받아들이지 않기로 했으면 그 이유를 같은 자리에 적는다. 무시하고 넘어가지 않는다.

### 승인 후 설계를 고쳐야 할 때

구현 중 설계가 틀린 것으로 드러났거나 전제가 깨졌으면(승인 게이트 5):

1. `approve: false`, `status: 승인대기` 로 내린다.
2. `## 설계` 끝 `### 개정 이력` 에 날짜와 사유를 적는다 — 다음 설계가 같은 함정을 반복하지 않도록.
3. 재승인은 다시 볼트에서 받는다. 스킬이 직접 되살리지 않는다.

## 1-M. UI 목업

`category: UI 개선`, 그리고 **화면 모양·동작이 바뀌는 모든 문제**에 적용한다.

글보다 그림이 빠르다. 승인 전에 **실제로 눌러볼 수 있는 HTML 목업**을 만들어 보여준다.
일괄 설계에서는 더 중요하다 — 사용자가 나중에 혼자 읽고 판단해야 하므로, 글만 있는 설계는 승인 판단이 불가능하다.

1. **기준 확보** — 임의로 새 화면을 상상하지 않는다. 순서대로 근거를 잡는다:
   - 현재 화면의 JSP/JS/CSS 를 읽어 실제 마크업·클래스·문구를 가져온다.
   - 사업 폴더나 사용자가 지정한 설계 목업(디자인 시안)이 있으면 그것을 우선 기준으로 삼는다.
   - **기준에 없는 문구·버튼·항목을 새로 만들지 않는다.** 이번 문제로 바뀌는 부분만 달라져야 하고, 나머지는 현재 화면 그대로여야 비교가 성립한다.
2. **작성** — `<VAULT>/첨부/목업/<사업명>/<ID>-<안>.html` 에 자기완결 HTML 한 파일로 만든다(외부 CDN·이미지 참조 금지, CSS/JS 인라인). 폴더가 없으면 만든다.
   - 방안이 여러 개면 **비교 대상 안마다 하나씩** 만든다(`FDR-002-1안.html`, `FDR-002-2안.html`). 사용자가 눈으로 고르는 것이 이 단계의 목적이다.
   - 변경 전/후 대비가 핵심이면 한 파일 안에 좌우로 나란히 배치한다.
   - 상호작용(버튼 클릭 → 상태 변화)이 설계의 요점이면 그 부분만 최소한의 인라인 JS 로 실제 동작하게 만든다. 서버 호출은 흉내만 낸다.
3. **보여주기** — 단건 설계면 사용자의 기본 브라우저로 연다(Windows: `start "" "<파일 경로>"`). 일괄 설계면 매 건 열지 않고 캡처 임베드로 갈음하되, 승인 단계에서 노트의 목업 링크로 열 수 있게 한다.
4. **캡처 후 설계에 삽입** — Playwright MCP 가 있으면 `file:///<경로>` 로 열어 캡처하고 `<VAULT>/첨부/스크린샷/<사업명>/<ID>-<안>.png` 로 저장한 뒤, `## 설계` 의 `### 목업` 절에 안별로 `![[<파일명>.png]]` 로 임베드한다. 목업 HTML 자체도 `[[<ID>-<안>.html]]` 로 링크해 나중에 다시 열 수 있게 한다.
   - 안이 여러 개면 `### 목업` 에 안별 캡처를 표로 나란히 놓아 `### 방안 비교` 표와 짝이 맞게 한다.
   - Playwright MCP 가 없거나 캡처가 실패하면 **중단하지 않는다.** 브라우저로 보여준 것으로 갈음하고, 캡처를 건너뛴 사실을 보고에 남긴다.
5. 사용자가 목업을 보고 고른 안이 있으면 `### 선택` 에 반영한다. 목업과 다르게 구현하게 되면 구현 단계에서 멈추고 보고한다.

## 1-B. 일괄 설계 (`설계`)

순차 실행한다. 앞 설계가 뒤 설계의 문맥이 되는 것이 이 방식의 값이다.

1. **대상 확정** — `status: 제안` 전부 또는 지정 ID. 건수를 알리고 진행 확인을 받는다.
2. **공통 문맥 1회 로드** — 대상이 같은 화면이면 진입점(컨트롤러→JSP→JS→매퍼) 지도를 먼저 만들고 전 건에서 재사용한다. 건마다 같은 파일을 다시 여는 낭비를 없앤다.
3. **문제 루프** — 절차 1 을 그대로 수행하고, 한 건이 끝나는 즉시 노트를 **저장**한다. 중간에 끊겨도 완료분은 디스크에 남고, 재실행하면 남은 `제안` 건부터 이어진다.
4. **교차 검토 1회** — 전 건 설계가 끝난 뒤 (일괄에만 있는 단계):
   - 변경 대상 파일이 겹치는 문제쌍을 표로 보고한다 → 합칠지 순서를 정할지는 사람이 판단
   - 서로 모순되는 설계(같은 요소를 다르게 바꿈)를 찾아 보고한다
   - 중복 문제(사실상 같은 원인)를 발견하면 통합을 제안한다
   - 나눠 돌려서 이 단계를 못 했으면 나중에 `설계 검토` 로 따로 수행한다 (이때는 `승인대기` 건 전체를 대상으로 한다)
5. **보고** — 설계 완료 목록, 겹침·모순 경고, 그리고 다음 안내:

   > 대시보드의 **승인 대기 설계** 표에서 각 설계를 열어 읽고 `승인` 을 체크하세요.
   > 체크된 건은 `/si-workbench:improve 구현` 에서 한 번에 적용됩니다.

   요청하면 승인대기 노트들을 옵시디언으로 연다.
6. SKILL.md 의 「전파」에 따라 `문제목록` 인덱스와 `개선.md` MOC 를 갱신한다.

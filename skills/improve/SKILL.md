# 개선 사이클 (improve)

사용자가 화면 단위로 발견한 문제를 **문제 기술서 → 설계 → 승인 → 구현(커밋) → 결과 보고** 순서로 처리한다.

승인은 **볼트에서만** 일어난다. 사용자가 설계 노트를 열어 `approve` 체크박스를 켜야 코드를 고칠 권한이 열린다.
채팅 발화로 코드가 바뀌는 경로는 존재하지 않는다.

설계는 여러 건을 한 번에 작성할 수 있고, 승인된 건들도 한 번에 구현할 수 있다.

이 파일은 **모든 실행에 공통인 것**만 담는다 — 안전 규칙·설정·구조·상태 머신·승인 게이트·스캔.
설계와 구현의 상세 절차는 아래 참조 파일에 있고, **어느 경로로 갈지 정해진 뒤에 해당 파일만 읽는다.**

## 안전 규칙 (최우선)

- **SVN 금지.** `svn status|info|log|diff|cat|list` 등 읽기 전용 조회만 허용. `commit`/`ci`/`add`/`revert`/`update`/`merge`/`switch`/`cleanup`/`propset` 등 상태를 바꾸는 하위 명령은 사용자가 요청해도 실행하지 않고 명령문만 알려준다. TortoiseSVN·`svn.exe` 절대경로·스크립트 경유도 동일하다.
- **원격 변경 금지.** `git push`, `git svn dcommit`, `hg push` 를 실행하지 않는다. 이 스킬의 범위는 **로컬 커밋까지**다.
- **승인 게이트.** 노트의 `approve` 가 `true` 가 아닌 문제의 코드는 절대 수정하지 않는다. 아래 「승인 게이트」의 불변식 6개를 지킨다.
- **범위 게이트.** 설계 문서의 `## 설계` > `### 변경 대상` 에 적히지 않은 파일은 건드리지 않는다. 구현 중 범위 밖 파일이 필요해지면 **멈추고 보고**한 뒤 설계를 갱신해 재승인받는다.
- **대상 프로젝트의 규약 준수.** 구현 전 프로젝트 루트의 `CLAUDE.md` 를 읽고 그 제약(수정 허용 패키지, 공통 파일 수정 금지 등)을 따른다. 제약과 설계가 충돌하면 구현을 멈추고 보고한다.
- **경로 한정 커밋.** 항상 파일 경로를 명시해 커밋한다. `git commit -a` / `git add .` / `git add -A` / 디렉터리 단위 `git add` 금지 — 무관한 미커밋 변경이 섞이면 되돌리기 단위가 깨진다. 경로 한정 커밋은 다른 파일이 스테이징돼 있어도 무시하고 그 스테이징 상태를 보존한다.
  - 예외: **추적되지 않은 신규 파일은 경로 한정 커밋이 거부**하므로(`error: pathspec ... did not match any file(s) known to git`), 신규 파일에 한해 `git add <파일 경로>` 로 **파일 하나씩** 명시 추가한 뒤 커밋한다.
- **되돌림도 경로 한정.** 구현을 폐기할 때 `git restore -- <변경 대상 파일>` 처럼 대상 경로를 명시한 명령만 쓴다. `git restore .` / `git checkout .` / `git reset --hard` 는 사용자의 다른 미커밋 작업을 지우므로 금지.
- **브랜치를 만들지도 옮기지도 않는다.** 개선 작업은 `workBranch` 한 곳에서만 진행한다(아래 「작업 브랜치」). 같은 작업 트리를 다른 세션·IDE·톰캣이 함께 보고 있으므로 `switch`·`checkout`·`branch -f`·`rebase`·`merge` 는 사용자만 실행한다. 스킬은 현재 브랜치를 **확인**만 하고, 다르면 멈추고 알린다.
- 볼트 쓰기는 개선 폴더 안에서만, 코드 쓰기는 승인된 문제의 변경 대상 안에서만 한다.

## 설정

`%USERPROFILE%\.claude\si-workbench\config.json` 에서 읽는다. 없으면 물어보고 저장한다 (PC마다 경로가 다르므로 하드코딩 금지).

```json
{
  "vaultPath": "C:\\Users\\me\\Documents\\WorkVault",
  "improve": {
    "defaultProject": "<사업명>",
    "projects": {
      "<사업명>": {
        "path": "D:\\workspace\\myproj",
        "workBranch": "improve/fdr",
        "portableBase": "origin/dev",
        "idPrefix": "FDR",
        "verify": "mvn -o -q compile"
      }
    }
  }
}
```

| 키 | 뜻 | 없을 때 |
|---|---|---|
| `path` | 코드베이스 절대경로 | 사용자에게 문의 |
| `workBranch` | **개선 작업 전용 단일 브랜치.** 모든 문제의 커밋이 여기 쌓인다 | 사용자에게 문의 (임의 생성 금지) |
| `portableBase` | 이 브랜치를 나중에 다른 브랜치로 옮길 때의 기준(예: `origin/dev`). 결과 문서 안내에만 쓴다 | 생략 |
| `idPrefix` | 문제 ID 접두어 | 사업명 이니셜로 제안 후 확인 |
| `verify` | 컴파일 검증 명령 | 생략 — 검증은 사용자 화면 확인으로만 |

`verify` 는 **반드시 `path` 루트에서** 실행한다. 다른 디렉터리에서 돌리면 수정하지 않은 트리를 컴파일하고 통과해 버린다.

- 볼트 경로 결정: `${user_config.vault_path}` → `config.json` 의 `vaultPath` → 사용자 문의.
- `improve` 블록이 통째로 없으면 이 스킬이 최초 1회 대화로 수집해 기록한다. 이후 실행에서는 다시 묻지 않는다.

### 작업 브랜치

개선 작업은 **`workBranch` 한 곳에서만** 진행한다. 문제마다 브랜치를 파지 않는다 — 브랜치를 오가면 같은 작업 트리를 보는 IDE·톰캣·다른 세션이 함께 흔들리고, 두 문제를 동시에 볼 수 없다.

- 되돌리기 단위는 브랜치가 아니라 **경로 한정 커밋 1개**다. 브랜치를 안 나눠도 `git revert <커밋>` 으로 그 수정만 걷어낼 수 있다.
- `workBranch` 는 **다른 사람의 변경이 섞이지 않은 지점에서 분기**해 두어야 나중에 통째로 다른 브랜치에 병합할 수 있다. 이 브랜치를 만들고 옮기는 일은 사용자가 직접 한다(스킬은 하지 않는다).
- 승인 후 이식이 필요하면 안내만 한다: `git rebase --onto <portableBase> <분기점> <workBranch>` 로 남의 커밋을 걷어낸 브랜치를 만들 수 있고, **이때 커밋 SHA 가 바뀌므로** 문제 노트의 `commits` 를 새 값으로 갱신해야 한다.

## 폴더·문서 구조

```
<VAULT>/사업/<사업명>/개선/
  개선.md                                  # MOC 대시보드 (상태별 전체 문제 표 + 구현 배치 이력)
  <화면단위>/                              # 예: fdrList.do — 요청 URL 1개 = 폴더 1개
    문제목록 - <화면단위>.md                # 인박스 겸 인덱스 (사용자가 자유 작성)
    <ID> <제목>.md                          # 문제 노트 — 문제·설계·결과가 한 노트
```

문제 노트 frontmatter (키는 영어, 값은 한국어. 스키마 밖 필드 생성 금지):

```yaml
---
type: 개선
id: FDR-001
screen_id: UI_LDM_FAB-1.1.6.2
screen: 내부보고서
url: fdrList.do
category: 버그              # 버그 | UI 개선 | 성능 | 리팩터링
status: 제안                # 제안 | 승인대기 | 승인 | 구현중 | 부분구현 | 구현완료 | 보류 | 반려
approve: false              # ★ 승인 체크박스. 사람만 true 로 만든다. 스킬은 false 로만 쓴다
approved: ""                # approve:true 를 스킬이 처음 관측한 날짜 (YYYY-MM-DD)
base: ""                    # 구현 시작 시점 HEAD. 일괄 구현이면 배치 시작 HEAD (배치 식별자 겸용)
branch: improve/fdr         # 개선 작업 브랜치 (workBranch 고정값)
commits: []
verified: 미확인            # 확인 | 부분확인 | 미확인
depends_on: []
dependents: []
related: []
---
```

본문 섹션은 `## 문제상황` / `## 원인 분석` / `## 설계` / `## 결과` 4개 고정. 템플릿은 `<VAULT>/템플릿/개선.md`.

`문제목록 - <화면단위>.md` 에는 frontmatter 를 두지 않는다. 인박스 겸 인덱스일 뿐이고 상태의 정본은 문제 노트다 — 두 곳에 상태를 두면 반드시 어긋난다.

문제 ID 는 사업 단위로 단조 증가한다(`FDR-001`, `FDR-002`, …). 화면이 달라도 번호는 이어 쓴다 — 커밋 메시지에서 전역적으로 유일해야 하기 때문이다. 새 ID 는 개선 폴더 전체를 스캔해 최대값 + 1 로 정한다.

파일명·폴더명의 Windows 금지 문자(`\ / : * ? " < > |`)는 제거하거나 `-` 로 치환한다.

## 상태 머신

```
        (스킬: 코드 조사 → ## 설계)        (사람: 볼트에서 approve 체크)
제안 ─────────────────────────▶ 승인대기 ─────────────────────────▶ 승인
 ▲                                 ▲ │                                │
 │        (스킬: 설계 개정 시        │ │ (사람: status 를 보류/반려)      │ (스킬: 구현)
 │         approve 자동 해제) ───────┘ ▼                                ▼
 │                                 보류 / 반려                       구현중
 │                                                                    │ (스킬: 경로 한정 커밋 1개)
 └──(사람: 되돌리기 <ID>)◀──── 구현완료 ◀────────────────────────────┘
                                  │
                                  └─(사람: 화면 확인) → verified: 확인
```

| 상태 | 스킬이 하는 일 | 다음에 사람이 할 일 |
|---|---|---|
| `제안` | 코드 조사 → `## 설계` 작성 → `승인대기` 로 전이 | — |
| `승인대기` | 설계 요약 제시 후 **정지**. 요청하면 노트를 옵시디언으로 연다 | **볼트에서 `approve` 체크** / `### 검토 의견` 작성 / `보류`·`반려` 로 변경 |
| `승인` | `approved` 기록 → 구현 → 커밋 | (단건이면 커밋 전 화면 확인) |
| `구현중` | 코드는 고쳤고 커밋 전. 재진입 시 「재진입 복구」로 분기 | 단건 모드의 화면 검증 |
| `부분구현` | 한 문제에 하위 항목이 여럿이고 일부만 적용했을 때. `## 결과` 의 `### 남은 것` 에 미착수분을 남긴다 | 남은 항목을 별도 ID 로 승격할지 결정 |
| `구현완료` | 목록·MOC 갱신 | 화면 확인 → `verified` 갱신 |
| `보류` `반려` | 스캔에서 접어 표시 (사유 유지) | — |

## 승인 게이트

이 6개가 이 스킬의 핵심 불변식이다. 하나라도 깨지면 승인 절차 전체가 무의미해진다.

1. **스킬은 `approve` 를 `true` 로 쓰지 않는다.** `false` 로 되돌리는 것만 허용된다(설계 개정 시).
2. 구현 직전 **디스크에서 노트를 다시 읽어** `approve: true` 를 확인한다. 세션 기억이나 앞선 스캔 결과를 믿지 않는다 — 한 세션에서 설계→승인→구현이 이어지는 경우가 가장 위험하다.
3. 채팅의 "승인해줘" / "그거 그냥 적용해" 는 승인이 아니다. 체크박스를 대신 켜지 말고, 해당 노트를 옵시디언으로 열어준 뒤 정지한다.
   ```powershell
   Start-Process "obsidian://open?vault=<볼트 폴더명>&file=<URL 인코딩한 볼트 상대경로(확장자 제외)>"
   ```
   **사용자가 재차 요구해도 마찬가지다.** 이 규칙은 사용자가 미래의 자신을 구속하려고 스스로 건 것이므로 스킬이 풀어주면 의미가 없다. 대신 노트를 열어주고 어디를 누르면 되는지 알려준다.
4. `approve: true` 인데 `## 설계` 의 `### 변경 대상` 표가 비어 있으면 **승인 무효**로 보고 정지한다. 설계 없이 체크만 켜진 상태에서 구현하지 않는다.
5. 승인 후 스킬이 설계를 고쳐야 하게 되면 `approve: false` + `status: 승인대기` 로 내리고, `## 설계` 끝 `### 개정 이력` 에 날짜와 사유를 적는다. 재승인 없이는 구현하지 않는다.
6. 검증(`verified`)은 게이트가 아니라 사후 기록이므로 채팅으로 갱신해도 된다. 승인만 볼트 전용인 이유는 **승인이 코드를 고칠 권한을 여는 행위**이기 때문이다.

### 반려·수정 요청 읽기

스캔할 때 `승인대기` 노트는 본문까지 읽는다(건수가 적다).

| 사람이 한 일 | 스킬의 반응 |
|---|---|
| `## 설계` 아래 `### 검토 의견` 에 내용이 있고 그 아래 대응 기록이 없다 | 그 문제를 재설계 대상으로 우선 제시한다. 의견 원문은 지우지 않고 그 아래에 대응을 적는다. `승인대기` 유지 |
| `status` 를 `보류` / `반려` 로 바꿨다 | 스캔에서 접어 표시. 적힌 사유는 유지 |

## 입력 (`$ARGUMENTS`)

| 형태 | 동작 | 읽을 참조 파일 |
|---|---|---|
| (없음) | 스캔 → 상태별 현황 표 → 다음 행동 제안 | 선택된 행동에 따라 |
| `등록` / `new` | 새 문제 노트 작성 대화 · 문제목록에서 승격 (→ `제안`) | `references/승격.md` |
| `설계` | `제안` 상태 전부를 순차 설계 (건수 확인 후 진행) | `references/설계.md` |
| `설계 <ID> <ID> …` | 지정 건만 설계 | `references/설계.md` |
| `설계 검토` | 이미 작성된 `승인대기` 건들의 교차 검토만 다시 수행 | `references/설계.md` |
| `검토` | `승인대기` 목록 출력 + 옵시디언으로 열고 **정지** | 없음 (승인 게이트 3번) |
| `구현` | `approve: true` 인 `승인` 건 전부를 일괄 구현 | `references/구현.md` |
| `구현 <ID>` | 단건 구현 (검증 후 커밋) | `references/구현.md` |
| `<화면단위>` | 그 화면의 문제만 스캔 | 선택된 행동에 따라 |
| `현황` / `status` | 대시보드만 출력하고 종료 (읽기 전용) | 없음 |
| `되돌리기 <ID>` / `revert <ID>` | 단건 되돌리기 | `references/구현.md` |
| `되돌리기 배치 <기준커밋>` | 같은 `base` 를 가진 배치를 역순 되돌리기 | `references/구현.md` |
| `<ID>` | 그 문제로 진입, 상태에 맞는 단계 1회 | 상태에 따라 |

## 참조 파일

경로는 `${CLAUDE_PLUGIN_ROOT}/skills/improve/references/` 다. **경로가 정해진 뒤에 해당 파일만 읽고 그대로 따른다** — 구현하러 왔는데 목업 작성법까지 읽을 이유는 없다.

| 파일 | 담긴 것 | 언제 읽나 |
|---|---|---|
| `승격.md` | 문제목록 → 문제 노트 분리 · 레거시 포맷 읽기 · 목록 문서 재작성 | `## 신규 (미승격)` 에 항목이 있거나 `등록` 일 때 |
| `설계.md` | 설계 작성(`제안` → `승인대기`) · UI 목업 · 일괄 설계와 교차 검토 | `설계` 경로일 때 |
| `구현.md` | 단건 구현 · 일괄 구현과 배치 리포트 · 커밋과 `## 결과` 작성 · 되돌리기(단건·배치) | `구현`·`되돌리기` 경로일 때 |

두 파일 모두 이 SKILL.md 의 안전 규칙·승인 게이트·금지사항을 전제로 쓰였다. 참조 파일이 이 문서와 어긋나 보이면 **이 문서가 우선**이다.

## 절차 0. 스캔 및 선택

모든 실행이 여기서 시작한다. 인자가 특정 경로를 지목했더라도 스캔은 먼저 한다 — 노트의 실제 상태가 정본이기 때문이다.

1. 설정을 로드하고 대상 사업을 정한다(인자가 없고 사업이 여러 개면 물어본다).
2. `개선/` 아래 모든 문제 노트의 frontmatter 를 읽는다. `승인대기` 노트는 본문의 `### 검토 의견` 까지 읽는다.
3. `문제목록 - *.md` 의 `## 신규 (미승격)` 섹션에 승격되지 않은 항목이 있으면 먼저 **0-A 승격**을 수행한다.
4. 상태별 현황을 출력한다:

   ```
   제안 8 · 승인대기 2 · 승인(구현 대기) 3 · 구현중 0 · 구현완료 3(검증대기 1)
   ```

   그리고 `구현완료`·`반려` 가 아닌 문제를 표로 출력한다:

   | ID | 화면 | 제목 | 구분 | 상태 | 승인 | 의존 |
   |---|---|---|---|---|---|---|

5. 다음 행동을 제안한다. 우선순위: 검토 의견이 달린 건 재설계 → 승인 건 구현 → 제안 건 설계 → 승인대기 건 검토 요청.
   **현재 상태에서 가능한 것만 선택지로 낸다** — 승인된 건이 0이면 "구현" 을 제시하지 않는다.
6. 사용자가 무엇을 할지 고르게 한다(AskUserQuestion). 선택지 설명에 "설계 8건 작성" / "승인된 3건 구현" 처럼 무엇이 일어나는지 명시한다.
   인자로 경로가 이미 지정됐으면(`설계`·`구현` 등) 이 질문은 건너뛴다.
7. 정해진 경로의 참조 파일을 읽고 그 절차를 따른다.

### 0-A. 승격 (문제목록 → 문제 노트)

`문제목록 - <화면>.md` 에 승격되지 않은 항목이 있을 때만 수행한다. 절차는 `references/승격.md` 를 읽고 그대로 따른다.
사용자가 한 파일에 자유롭게 적어둔 문제를 문제 노트로 분리하고(`status: 제안`, `approve: false`), 목록 문서를 인덱스 + 신규 작성 영역 구조로 재작성한다.
원본을 덮어쓰기 전에 반드시 확인을 받는다.

## 전파 (모든 볼트 쓰기 후 공통)

문제 노트를 고쳤으면 파생 문서도 같은 실행에서 맞춘다. 순서: frontmatter → `문제목록` 인덱스 표 → `개선.md` MOC → 사업 허브(`<사업명>.md`) 의 `## 문서` 에 개선 MOC 링크가 없으면 추가.

`개선.md` 가 없으면 이때 만든다. 구성은 `# <사업명> 개선` 제목 + 화면별 목록 문서 링크 + 상태별 문제 표(승인 대기 / 승인됨·구현 대기 / 진행중 / 제안 / 구현완료 / 보류·반려) + `## 구현 배치` 표.
본문은 문제 노트 frontmatter 에서 파생시키고 별도 서술을 쌓지 않는다 — 매 실행마다 통째로 다시 만들어도 같은 결과가 나와야 한다.

## 금지사항

| 금지 | 대안 |
|---|---|
| **`approve` 를 `true` 로 쓰기** | 사람만 볼트에서 켠다. 스킬은 노트를 옵시디언으로 열어주고 정지 |
| 채팅 승인만 받고 구현 시작 | 재차 요구받아도 거절. 노트를 열어주고 어디를 누르면 되는지 안내 |
| 세션 기억으로 승인 상태 판단 | 구현 직전 디스크에서 노트 재확인 |
| `### 변경 대상` 이 빈 채로 `approve: true` 인 건 구현 | 승인 무효로 보고 정지 |
| 승인 후 설계를 고치고 그대로 구현 | `approve: false` + `승인대기` 로 내리고 `### 개정 이력` 기록 → 재승인 |
| `svn` 상태 변경 명령 실행 | 읽기 전용 조회만. 필요한 명령은 사용자에게 문자열로 안내 |
| `git push` / `git svn dcommit` | 로컬 커밋까지가 범위 |
| `git commit -a`, `git add .`, `git add -A`, 디렉터리 `git add` | 파일 경로를 하나씩 명시. 신규 파일만 `git add <파일>` 후 커밋 |
| `git restore .`, `git checkout .`, `git reset --hard` | 폐기도 `git restore -- <변경 대상 파일>` 로 경로 한정 |
| 사용자 미커밋 변경에 `stash`/`reset`/`checkout .` | 그대로 두고, 겹치면 경고 후 확인 |
| 문제마다 브랜치 생성 / `switch`·`branch -f`·`rebase`·`merge` 실행 | `workBranch` 한 곳에 경로 한정 커밋만 쌓는다. 브랜치 조작은 사용자 몫 |
| **일괄 구현에서 커밋을 미루고 여러 건 쌓기** | 문제마다 즉시 커밋. 안 그러면 되돌리기 단위가 소멸 |
| 일괄 구현 중 실패 시 배치 전체 중단 | 실패 건만 restore 후 계속. 같은 파일 후속 건만 건너뜀 |
| UI 변경을 글 설명만으로 승인받기 | HTML 목업 → 캡처 임베드 (`references/설계.md` 의 1-M) |
| 목업에 현재 화면·시안에 없는 문구·요소 추가 | 이번 문제로 바뀌는 부분만 다르게, 나머지는 현재 화면 그대로 |
| Playwright MCP 부재로 설계 중단 | 브라우저로 보여준 것으로 갈음하고 건너뛴 사실 보고 |
| `구현중` 재진입 시 상태 확인 없이 재구현 | 커밋 여부·브랜치·변경 잔존을 먼저 확인하고 분기 |
| 문제 하나를 여러 커밋으로 분산 | 커밋 1개 원칙. 불가피하면 `commits` 에 전부 적고 되돌리기 순서를 역순으로 명시 |
| 설계 `변경 대상` 밖 파일 수정 | 멈추고 보고 → 설계 갱신 → 재승인 |
| `depends_on` 만 적고 상대 노트 미갱신 | 양방향(`dependents`) 동시 기록 |
| 검증 없이 `verified: 확인` 기재 | 확인 못 했으면 `미확인` 으로 정직하게 기록 |
| 스키마 밖 frontmatter 필드 | `docs/design.md` 의 개선 스키마만 사용 |
| 사용자 문장을 임의로 요약·윤색해 승격 | 원문 그대로 이동, 스킬의 판단은 별도 섹션에 |
| 참조 파일을 안 읽고 기억으로 설계·구현 절차 수행 | 경로가 정해지면 해당 참조 파일을 읽고 그대로 따른다 |

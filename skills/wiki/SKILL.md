# 위키 규범 (개념 노트)

이 스킬은 si-workbench 위키 규범의 단일 진실원천(single source of truth)이다.
다른 모든 si-workbench 스킬(daily-log, daily-report, project-doc, codebase-docs)은
vault에 노트를 쓸 때 이 규범을 준수함을 각자 본문에 명시한다.

## 공통 정책

- 코드베이스는 읽기 전용으로만 다룬다. 어떤 파일도 수정/삭제하지 않는다.
- 원격 변경 금지: `git push`, `svn commit/ci`, `git svn dcommit`, `hg push`는 실행하지 않는다. 로컬 작업만 한다.
- vault 루트 경로 결정 순서: 1) `${user_config.vault_path}` (비어있지 않으면 최우선) 2) `%USERPROFILE%\.claude\si-workbench\config.json`의 `vaultPath` 3) 둘 다 없으면 `/si-workbench:setup` 실행을 안내하거나 사용자에게 절대경로를 묻는다. 개념 노트 위치: `<vault>/개념/<개념명>.md`.

## 규범 7조

### 제1조 — 개념 첫 등장 시 위키링크

문서에 개념이 처음 등장하면 `[[개념명]]` 위키링크로 표기한다. 같은 문서 내 두 번째 등장부터는 일반 텍스트로 써도 된다.

절차:
1. 문서를 작성/수정하다 개념 용어를 만난다.
2. 이 문서에서 첫 등장인지 확인한다.
3. `[[개념명]]`으로 표기한다.
4. 해당 노트가 없으면 아래 "개념 노트 생성 절차"로 노트를 만든 뒤 링크한다. 링크만 남기고 노트가 없는 상태(죽은 링크)로 두지 않는다.

### 제2조 — 개념 노트는 짧고 단일하게

개념 노트 본문은 2-3문장 정의면 충분하며, 출처는 frontmatter `sources`, 관련 노트는 `related`에 둔다.
다른 노트와 본문이 겹치지 않게 한다. 같은 설명을 여러 노트에 복사하지 않고, 한 노트에만 정의한 뒤 나머지 노트는 `[[링크]]`로 연결한다.

### 제3조 — 기능분석 문서의 경로 격리

기능분석 문서에서 실제 파일 경로는 frontmatter `sources`에만 적는다.
본문은 추상 서술과 mermaid 다이어그램으로 쓴다. 경로가 바뀌어도 본문이 썩지 않는 구조가 목적이다.

### 제4조 — 사업 허브는 MOC

`${user_config.vault_path}/사업/<사업명>/<사업명>.md` 허브는 분석 문서, 주요 개념, 산출물의 링크 목록(MOC)이다.
문서를 추가하거나 개념 노트를 새로 만들 때마다 허브 목록을 최신으로 유지한다.

허브의 링크 목록은 Bases 뷰로 대체하지 않는다. Base는 쿼리이지 링크가 아니어서 백링크·그래프에 잡히지 않기 때문이다.
역할 분리: 허브의 `related`와 본문 링크 = 관계(백링크가 걸린다), `.base` = 열람(필터·정렬·전체 목록).

### 제5조 — 프로퍼티는 템플릿 스키마만

frontmatter 필드는 템플릿 스키마만 사용한다. 개념 노트 스키마(순서 고정):

| 키 | 값 |
|---|---|
| `type` | `개념` |
| `domain` | 분류 (통제 어휘 1개): `기술` `업무도메인` `행정용어` `제도·법령` `조직·기관` `시스템·제품` |
| `status` | `확인필요` → `초안` → `정리됨` (아래 "개념 수집" 절 참조) |
| `aliases` | 별칭 목록 (없으면 비움) |
| `related` | 관련 노트 `[[링크]]` 목록 |
| `sources` | 출처 목록 (제안서명, 코드 경로, 회의 노트 등) |
| `tags` | 태그 목록 |

`domain`은 분류를 책임지는 단일 값이므로 `tags`에 같은 분류를 중복해 적지 않는다. `tags`는 자유 태그 전용이다.
`status: 확인필요`는 이름만 적어두고 뜻은 아직 모르는 용어다. 이 값이면 `개념.base`의 수집 뷰와 대시보드 「개념 수집함」에 모인다.

키는 영어, 값은 한국어. 모르는 값은 비워둔다. 다른 노트 유형의 스키마는 `${user_config.vault_path}/템플릿/`의 각 템플릿이 기준이다.

### 제6조 — 테이블은 저장이 아니라 뷰다

개념은 예외 없이 노트 1개다. "단순한 용어는 표에 한 줄로, 복잡한 개념만 노트로" 같은 이원 저장을 만들지 않는다.
한 줄짜리 용어도 노트로 만든다 — `[[위키링크]]`는 노트가 있어야 성립하고(제1조), 표의 한 행은 링크 대상이 될 수 없기 때문이다.

표로 훑어보고 싶은 요구는 Obsidian **Bases**(코어 플러그인)가 담당한다. Bases는 노트의 frontmatter를 읽어 표로 그리는 뷰일 뿐이므로,
`.base` 파일을 전부 지워도 지식은 노트에 그대로 남아야 한다. 그래서:

- `.base` 파일에 정의 본문이나 설명을 적지 않는다. 필터·정렬·표시할 프로퍼티만 적는다.
- **모든 `.base`는 `템플릿/` 폴더를 제외한다.** 템플릿 노트도 `type: 일지`·`type: 사업` 같은 실제 값을 갖고 있어서, `type`으로만 거르면 템플릿이 결과에 섞인다. 최상위 `filters`에 아래를 넣는다(폴더로 거르는 base는 이미 제외되므로 불필요):
  ```yaml
  filters:
    and:
      - type == "일지"
      - not:
          - file.inFolder("템플릿")
  ```
  `!` 로 시작하는 부정 표현은 YAML이 태그로 읽으므로 `not:` 절을 쓴다.
- 표에서 구분하고 싶은 축은 새 폴더가 아니라 **프로퍼티**로 만든다. `개념/`은 평면 폴더로 유지하고 `domain`으로 나눈다.
- 표준 `.base` 위치: `개념/개념.base`, `사업/사업.base`, `사업/개선.base`, `일지/일지.base`. 볼트 루트 `대시보드.md`가 이들의 뷰를 임베드한다.
- 표에서 바로 개념을 붙잡을 수 있게 `개념.base`는 `newItemFolder: 개념`과 `newItemTemplate: 템플릿/개념.md`를 갖는다. 새 항목 버튼이 템플릿 frontmatter를 씨앗으로 `개념/`에 노트를 만든다 — 표에 한 줄 추가하는 동작이 곧 노트 생성이므로 이원 저장이 생기지 않는다.
- `.base` 스키마(Obsidian 1.13 기준): 최상위 키는 `filters` `views` `properties` `formulas` `summaries` `newItemFolder` `newItemTemplate`.
  각 view는 `type`(필수)·`name`(필수)과 `filters` `order` `sort`(`{property, direction: ASC|DESC}`) `groupBy`(`{property, direction}`) `limit`를 갖는다.
  다른 노트에서 특정 뷰를 임베드할 때는 `![[파일.base#뷰이름]]`.

### 제7조 — 제목은 파일명이 갖는다

노트 본문 첫 줄에 파일명과 같은 `# 제목` H1을 쓰지 않는다.

Obsidian은 에디터 최상단에 파일명을 인라인 제목으로 이미 보여준다. 같은 문자열을 H1으로 한 번 더 쓰면 화면에 제목이 두 번 나오고,
이름을 바꿀 때 파일명과 H1 두 곳을 함께 고쳐야 해서 어긋나기 쉽다. 그래서:

- 템플릿에 `# {{title}}` 줄을 두지 않는다. 노트는 frontmatter → 안내 주석 → 첫 `##` 섹션 순으로 시작한다.
- 어떤 스킬이든 새 노트를 만들 때 H1을 넣지 않는다. 본문 헤딩은 `##`부터 시작하고, 그 아래는 `###`로 내려간다.
- **파일명이 담지 못하는 정보가 H1에 있을 때만 예외다.** 파일명이 줄임말이거나 `/` 같은 파일명 금칙문자 때문에 달라진 경우
  (예: `내부망_외부망_Apache_구조.md` → `# 내부망/외부망 Apache 통신 구조`)는 H1을 남긴다. 이때 H1을 파일명과 같은 문자열로 고쳐 맞추지 않는다 — 정보가 줄어든다.
- 일지 노트의 날짜는 파일명(`YYYY-MM-DD.md`)이 갖는다. `# 2026-09-03` H1도, `date` 프로퍼티도 만들지 않는다.

볼트 위생 점검이 `[제목중복]`으로 파일명과 같은 H1만 찾아 지운다. 파일명과 다른 H1은 건드리지 않는다.

## 개념 수집 (status 흐름)

용어는 뜻을 모르는 채로도 먼저 붙잡아 둔다. 상태는 한 방향으로만 올라간다:

| status | 뜻 | 어디에 보이나 |
|---|---|---|
| `확인필요` | 이름만 적어둔 상태. 정의가 없다 | `개념.base` 수집 뷰, 대시보드 「개념 수집함」 |
| `초안` | 정의는 썼지만 `sources`가 비었다 | 수집 뷰 + 근거없음 뷰 |
| `정리됨` | 정의와 출처가 모두 있다 | 전체 / 분류별 뷰 |

수집 경로는 셋이다.

- **한 건씩** — 사용자가 `개념.base`의 수집 뷰(또는 대시보드 「개념 수집함」)에서 새 항목 버튼으로 행을 추가한다. `newItemFolder: 개념` + `newItemTemplate: 템플릿/개념.md` 설정 때문에 `개념/<이름>.md`가 `status: 확인필요`로 생긴다. 스킬은 이 노트를 지우거나 옮기지 않는다.
- **문맥과 함께 메모로** — 사용자가 아무 노트에나 `## 개념 수집` 섹션을 만들어 용어를 문맥째로 적어 둔다. 볼트 위생 점검이 `[수집]`으로 잡아 주며, 아래 "수집 메모 승격" 절차로 올린다. 단어만으로 뜻이 갈리는 용어(동음이의어)는 이 경로를 쓴다.
- **여러 건 한꺼번에** — 사용자가 용어 목록(회의 메모, 엑셀 붙여넣기, 일지 수기 기록 등)을 주면 각각에 대해 "개념 노트 생성 절차"를 돌려 `status: 확인필요` 스텁 노트를 만든다. 정의를 모르면 **추측해서 쓰지 않는다.** `## 정의`를 비워 두고 `확인필요`로 남긴다. 근거 없는 정의를 쓰는 것보다 비어 있는 편이 낫다.

"개념 정리해줘"처럼 대상이 특정되지 않은 요청을 받으면 `status: 확인필요` → `초안` 순으로 오래된 것부터 처리한다. 처리란 정의를 채우고 `domain`·`sources`·`related`를 붙여 상태를 한 단계 올리는 것이다.
사용자에게 물어봐야 뜻을 알 수 있는 용어(사내 관행, 발주처 내부 용어)는 `확인필요`로 남기고, 보고에 "확인 필요 목록"으로 모아서 제시한다.

### 수집 메모 승격 (`## 개념 수집`)

용어 하나만 떼어 적으면 뜻이 갈리는 경우가 많다(예: `임상` — 산림에서는 林相이지만 의료에서는 臨床). 그래서 **문맥째로 적어두고 나중에 승격**하는 경로를 둔다.

사용자는 **아무 노트에나** `## 개념 수집` 섹션을 만들고 용어를 문맥과 함께 적는다. 일지의 한 섹션이든, 사업 노트든, 루트에 만든 임시 메모든 상관없다. 볼트 위생 `scan`/`fix`가 이 섹션에서 아직 승격되지 않은 줄을 `[수집]`로 뽑아 준다.

승격 절차:

1. **문맥을 먼저 읽는다.** 섹션의 머리글(예: "산사태 정보 시스템에서 검토 대상을 찾을 때 쓰는 용어")과 각 줄의 괄호·부연이 곧 의미를 가르는 단서다. 이 문맥 없이 일반 상식으로 정의를 쓰지 않는다 — 동음이의어를 엉뚱한 뜻으로 박아 넣는 사고가 여기서 난다.
2. **줄마다 용어를 판별한다.** 한 줄에 용어 하나가 원칙이고, 괄호·쉼표 뒤는 문맥으로 취급한다. 줄이 서술문이면(머리글 등) 용어가 아니므로 승격하지 않고 그 섹션 전체의 공통 문맥으로 쓴다.
   - 점검 스크립트도 같은 규칙을 쓴다: **목록(`- `)이 하나라도 있는 섹션에서는 목록이 아닌 줄을 공통 문맥으로 보고 승격 후보에서 뺀다.** 목록이 전혀 없는 섹션은 한 줄에 용어 하나로 적은 것이므로 모든 줄이 후보다. 그래서 머리글을 매번 "승격 대기"로 다시 물어보지 않는다.
3. **개념 노트 생성 절차**를 돌린다. 이때:
   - `## 정의` — 문맥으로 확실히 말할 수 있는 만큼만 쓴다. 확실하지 않으면 비워 두고 `status: 확인필요`로 남긴다.
   - 사용자가 적은 부연은 **원문 그대로** 노트에 남긴다(`## 정의` 아래 인용 또는 `## 관련`). 요약하거나 다듬어 없애지 않는다.
   - 동음이의어면 `aliases`에 한자·영문 표기를 넣고, 정의 첫 문장에서 이 볼트가 쓰는 뜻을 못 박는다.
   - 원본 노트는 `related`에 `[[링크]]`로 남긴다. **`sources`에 넣지 않는다** — 원본은 용어를 어디서 봤는지일 뿐 정의의 근거가 아니다. 확인한 근거 없이 쓴 정의는 `sources: []` + `status: 초안`이 정확한 표시이고, 이 상태가 나중에 근거를 찾아 채울 대상 목록이 된다.
   - `domain`은 문맥에서 정한다. 애매하면 가장 가까운 값 + `status: 확인필요`.
4. **원본 줄에 링크를 건다.** 용어 부분만 `[[용어]]`로 감싸고 **나머지 문장은 손대지 않는다.** 줄을 지우거나 링크만 남기고 문맥을 버리지 않는다. 사용자가 쓴 글은 그 자리에 그대로 있어야 한다.
   - 예: `- 임상(항목에는 침엽수, 활엽수 이렇게 있음)` → `- [[임상]](항목에는 침엽수, 활엽수 이렇게 있음)`
   - 이 링크가 곧 "승격 완료" 표시다. `[[`가 있는 줄은 다음 점검에서 건너뛰므로 재실행해도 중복 생성되지 않는다(멱등).
5. **보고** — 승격한 용어, 각각의 `domain`/`status`, 그리고 뜻을 확정하지 못해 `확인필요`로 남긴 것을 목록으로 낸다. 마지막 목록이 곧 담당자에게 물어볼 용어 목록이다.

`## 개념 수집` 섹션이 없는 곳에 적힌 메모(예: 볼트 루트에 만든 낱장 노트)는 `[미분류]`로 잡힌다. 성격이 용어 목록이면 같은 절차로 승격하고, 원본 노트는 사용자가 지우라고 하기 전까지 **삭제하지 않는다.**

## 개념 노트 생성 절차

1. 기존 노트 검색: `${user_config.vault_path}/개념/` 아래에서
   - 파일명이 개념명(또는 별칭)과 일치하는지,
   - 기존 노트들의 frontmatter `aliases`에 개념명/별칭이 있는지 확인한다.
2. 노트가 있으면 새로 만들지 않는다. 정의나 출처가 부족하면 기존 노트의 기존 필드 안에서만 보완한다.
3. 노트가 없으면 템플릿 복제: `${user_config.vault_path}/템플릿/개념.md` → `${user_config.vault_path}/개념/<개념명>.md`.
   - vault에 템플릿이 없으면 `${CLAUDE_PLUGIN_ROOT}/templates/개념.md`를 사용한다.
   - 그것도 없으면 `/si-workbench:init-vault` 실행을 안내하고 이 절차를 중단한다.
4. 내용 기재:
   - `## 정의`에 2-3문장 정의를 쓴다. 한 줄로 끝나는 용어여도 노트로 만든다(제6조).
   - `sources`에 실제 출처를 남긴다. 제안서 문서명, 코드 경로, 회의 노트 링크 등 확인 가능한 근거만.
   - `related`에 관련 노트 `[[링크]]`를 채운다.
   - `domain`을 제5조 어휘 중 하나로 정한다. 판단이 서지 않으면 비워두지 말고 가장 가까운 값을 넣은 뒤 `status: 확인필요`로 표시한다.
   - `status`를 정한다: 정의와 `sources`가 모두 있으면 `정리됨`, 정의는 썼지만 근거가 없으면 `초안`, 이름만 있고 뜻이 미확인이면 `확인필요`.
5. 링크 연결: 원래 문서의 해당 용어가 `[[개념명]]`으로 링크되어 있는지 확인하고, 제4조에 따라 관련 사업 허브의 주요 개념 목록에도 추가한다.

## 금지사항

| 금지 | 대신 |
|---|---|
| 템플릿에 없는 프로퍼티 필드 임의 생성 | 제5조 스키마의 필드만 사용 |
| 노트 없는 `[[링크]]` 방치 (죽은 링크) | 링크 전에 개념 노트 생성 절차로 노트 확보 |
| 노트 간 본문 중복 (같은 설명 복사) | 한 노트에만 정의, 나머지는 `[[링크]]`로 연결 |
| 프로퍼티 값 영어화 | 값은 한국어 (키와 코드 식별자만 영어) |
| 코드베이스 수정 또는 원격 변경 (`git push`, `svn commit`) | 읽기 전용, 로컬 작업만 |
| 용어를 노트 없이 표(또는 `.base`)에만 기록 | 개념은 항상 노트 1개, 표는 Bases 뷰로 (제6조) |
| 파일명과 같은 `# 제목` H1 작성 | 본문은 `##`부터 시작 — 제목은 파일명이 갖는다 (제7조) |
| 뜻을 모르는 용어에 추측 정의 작성 | `## 정의`를 비우고 `status: 확인필요`로 남긴 뒤 확인 필요 목록에 올린다 |
| `확인필요`/`초안` 스텁 노트를 "빈 노트"로 보고 삭제 | 수집된 상태이므로 보존 — 정리 대상이지 삭제 대상이 아니다 |
| `.base` 파일에 정의 본문 작성 | `.base`는 필터·정렬만, 지식은 노트에 |
| `domain` 분류를 폴더 분리로 표현 | `개념/`은 평면 유지, 분류는 `domain` 프로퍼티 |
